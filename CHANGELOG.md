# Changelog

All notable changes to Prism are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- **Page kinds beyond the feature pipeline.** The wiki has `topics/` (synthesis), `research/` (one question and its current answer) and `plans/` (the current status of a plan, with no history), each with a `_FORMAT.md`, and the single pages `direction.md` (the current direction and principles) and `roadmap.md` (what comes next; a date about the world may appear in it), which `SCHEMA.md` defines. Every kind has front matter with `kind` (the kind of its folder), `sources` and, for a topic, research page or plan, a `title` and a `status` (topic `draft` or `current`; research `open` or `concluded`; plan `proposed`, `active`, `paused`, `done` or `dropped`). The formats carry no history date and show the evidence labels. `prism wiki lint` validates the front matter of each kind (`missing-<kind>-kind`, `invalid-<kind>-kind`, `invalid-<kind>-title`, `missing-<kind>-status`, `invalid-<kind>-status`, `missing-<kind>-frontmatter` and `invalid-<kind>-sources`, with `<kind>` one of `topic`, `research`, `plan`, `direction` and `roadmap`), applies the history-date, evidence-label, superseded-decision and relative-link checks to them, and the graph no longer reports a link to one of these pages as dangling.
- **`ingest`, a generic intake skill for any role and any page kind.** It processes one pending folder into a topic, research page, plan, direction, roadmap, persona, business rule, decision (ADR) or new feature, with the evidence labels, the date-slug processed source, the conflict quarantine and the current-state replacement rules. `po-intake` and `design-intake` remain the role-specific entry points. The connected board accepts `ingest` as a write skill (25 canonical skills) with a validator built on the intake validators: a new feature meets every `po-intake` rule; a topic, research page, plan, direction or roadmap page is created or replaced in place; a persona, business rule or decision is created and never rewritten, except that a new decision with `supersedes: ADR-NNN` comes with the old ADR changed in its status fields only (`record_immutable` and `supersession_incomplete` otherwise); the manifest lists every written page by path and canonical ID. New rejection codes are `invalid_topic`, `invalid_research`, `invalid_plan`, `invalid_direction`, `invalid_roadmap`, `wiki_path_invalid`, `invalid_decision` and `decision_path_mismatch`.
- **The general index lists every wiki page.** `index.md` has one line per page, in the present tense, grouped by kind (`- [F-001 User login](features/F-001-login.md): Users sign in with an email address.`), with no dates and no narrative; a changed page's line is replaced in place. The connected board adds or replaces the line of each page it writes, derived from the page's title and the first sentence of its summary, and merges it by page with the same conflict, idempotence and recovery guarantees as the status rows (`stale_index_entry`, `duplicate_index_entry`). `prism wiki lint` reports `missing-index-entry`, `orphan-index-entry` and `duplicate-index-entry` as warnings on `index.md`; they never block a lifecycle action.
- **`prism wiki search` and `wiki-query` read the index first.** The index lines that contain the query name their pages, which come first in `facts.results` with their `index_line` and `index` among the `matched_fields`; `facts.index_match_count` counts them, and the index is listed first under `sources`. Every page folder, including the new kinds, is still searched by its own fields. The `wiki-query` skills say so in both layers.
- **Evidence labels on current-state pages.** `SCHEMA.md` defines five labels, written as a bold run-in label at the start of a list item or paragraph: `**Decided:**`, `**Observed:**`, `**Proposed:**`, `**Assumed:**` and `**Unknown:**`. A Decided or Observed claim links its evidence: a processed intake item, a record or a URL. A feature's `## Open questions` table is its Unknown form. Each page format's example shows the labels, and operational rules 12 to 15 state the current-state rule (replace superseded content in place, rationale as a current fact, history in `log.md` and the records), the labeling rule, the rule that records and raw sources are never rewritten, and the quarantine rule. `prism wiki lint` reports a Decided or Observed item without a link as the warning `unlinked-claim`, and a bold run-in label that is none of the five as the warning `unknown-evidence-label`. Lint checks the form only and never whether the evidence supports the claim.
- **Decision supersession.** An ADR can carry `supersedes: ADR-NNN`, and a superseded ADR carries `status: superseded` and `superseded-by: ADR-MMM` with its body unchanged. `SCHEMA.md` defines the decision-supersession workflow as one operation that also updates the current-state pages that relied on the old decision. `prism wiki lint` reports links that disagree or are missing as the error `supersession-mismatch`, and a current-state page that links a superseded ADR as the warning `superseded-decision-cited`.
- **Dated, immutable raw sources.** Intake folders are named `YYYY-MM-DD-slug/` under `pending`, `processed` and `quarantined`, and a processed item keeps a `MANIFEST.md`. The connected board rejects a move whose folder has another name with `intake_name_invalid`, and a write into an existing processed item, or a move onto one, with `processed_source_immutable`. `prism wiki lint` warns with `processed-source-without-manifest` when a processed item has no manifest. `intake/README.md` says how to archive an agent review packet or an agent output as a source, and the intake templates carry a `Captured:` line that matches the folder's date.
- **Conflict quarantine records.** A source that contradicts an existing page moves to `intake/quarantined/YYYY-MM-DD-slug/` with a `CONFLICT.md`: front matter `status: open | resolved`, and an `## Existing claim` and an `## Incoming claim` section, each with `**Claim:**`, `**Scope:**` and a linked `**Evidence:**`. The existing page stays untouched until a human resolves the conflict. `prism wiki lint` reports each open conflict as the warning `unresolved-conflict` (a non-empty quarantine is not a gate) and a record that does not follow the format as the error `malformed-conflict`. The board accepts a quarantine only as a valid `CONFLICT.md` with `status: open` and no wiki change (`conflict_report_invalid`, `quarantine_write_scope`).
- **`history-date-on-page`, `malformed-log-entry` and `missing-schema-version` lint findings.** `prism wiki lint` reports a history-date field (`introduced`, `last-updated`, `created`, `updated`, `date-updated` and similar, in any spelling) in the front matter of a current-state page as the error `history-date-on-page`, with a message that points to `log.md`. An ADR keeps its `date` and an advisory review its `reviewed`, because a dated record's date is part of what it records. A `log.md` entry that is not in the log format is the warning `malformed-log-entry`: lint reports it and never rewrites the log. `SCHEMA.md` or `LIFECYCLE.md` without the front matter `schema-version: 1` is the error `missing-schema-version`.
- **A "Project docs" group in the general index.** A generated workspace's `knowledge/wiki/index.md` lists each template-owned `docs/` page once, as `- [Architecture](../../docs/architecture.md): System design, platform map, tech decisions and the auth flow.`, so an agent finds the human docs from the wiki. `prism wiki lint` holds these lines to the rules of the other index lines: `orphan-index-entry` for a line whose doc does not exist and `duplicate-index-entry` for a doc listed twice. A doc without a line is not a finding, and `wiki search` does not return docs. A workflow-only workspace has no such group.
- **`prism workflow install` adds the index lines of the pages it installs.** When it keeps your own `knowledge/wiki/index.md`, it appends a line for each page it creates (`CONNECTED.md`, `status-board.md`, `direction.md`, `roadmap.md` and similar), in that page's group, and changes no line you wrote, so adoption no longer leaves `missing-index-entry` warnings for those pages.
- **Link and source checks.** Every relative Markdown link and every `sources` entry of a wiki page must resolve to an existing file or folder. `prism wiki lint` reports one that does not, or that leaves the workspace, as `broken-link` (error, naming the page, the link and the line), and an anchor that no heading of its target gives as `broken-anchor` (warning). Links in code, URLs, images and absolute paths are not checked, and no URL is fetched. A feature's `sources` entries are paths; a persona, business rule, topic, research page, plan, `direction.md` or `roadmap.md` may hold URLs or free text, so only an entry that is a `knowledge/` path is checked, and a pending intake path names the processed path to list. Only a broken link to a page of the wiki gates a lifecycle action, as before; the other link findings never block.
- **`repo:<repository-id>/<path>` links into an external repository.** In a body link or a `sources` entry, `repo:mobile-apps/apps/partner/Login.kt` names a file or folder of a repository of `prism.workspace.yml` (`workspace` is this repository). Lint resolves it through the untracked `prism.local.yml` and only checks that the path exists: it never reads a file in a checkout, never follows a symlink inside one and never writes there. A repository with no checkout gives one `external-repository-unresolved` warning for that repository, however many links point into it, and its links are skipped. A path missing from a resolved checkout, an undeclared repository id and a malformed link are `broken-link`. `SCHEMA.md`, `docs/workspace-model.md` and `docs/wiki-workflow.md` define the form.
- **Freshness from the log.** A verification is a `log.md` entry whose operation is `verify`; the pages on its `paths` line were checked against their sources that day. For each current-state page, lint takes the latest `verify` entry that lists it and reports `stale-page` (warning) when it is older than `wiki-stale-after-days` (14 when `SETTINGS.md` is absent or invalid) and `never-verified` (information) when there is none, so an overdue page is not confused with one that nobody has checked. Records, the log, the index, the status board, the schema files and generated files are exempt. Freshness never changes a status and never blocks a lifecycle action or a board write. `never-verified` appears in `prism wiki lint` and its JSON only; `stale-page` appears wherever diagnostics do, and it keeps a graph node healthy.
- **`prism wiki verify <page>... [--evidence <link>] [--by <name>]`.** It appends one `verify` entry to `knowledge/wiki/log.md` and changes nothing else. A page is named from the workspace root or from the wiki. The command refuses a path outside the wiki, a page that does not exist and a page that is not a current-state page, and writes nothing when it refuses any page. It appends the way the board does: it rejects a symlink or reparse point on the path, swaps the log in atomically only while it is unchanged and reads it again when another writer got in between.
- **`verify-pages`, a canonical skill that records a verification through the board.** `preview_skill` with an empty `changes` list and the verified pages in `read_revisions`, each with the digest `read_workspace` returned, previews one `verify` entry in `log.md`; `apply` is refused as stale when a verified page changed after the preview. Like every skill write it is for agents, and the entry's `by` names the agent. `verify-pages` is the 26th canonical skill; the packaged workflow asset and its digest change, so existing grants need `prism workflow upgrade`.

### Changed

- **`broken-wiki-link` is `broken-link`.** It covers every relative Markdown link, to a file or a folder inside or outside the wiki, and every `sources` entry. A link to a file that is not in the wiki used to go unchecked.
- **`prism wiki lint` lists the warnings and information of a wiki without errors.** After `Wiki contract checks passed.` it prints a Findings section; before, only the counts showed.
- **Stale items are `stale-page` findings.** The `wiki-owner`, `lint-wiki` and `wiki-blockers` skills, `docs/generated-projects.md` and the generated `AGENTS.md` describe staleness as the log-derived `stale-page`, and the direct-read fallback of `wiki-owner` computes it from the `verify` entries of `log.md`.
- **An ADR's status is `superseded` with a `superseded-by` field.** The earlier `status: superseded-by ADR-XXX` form is an `invalid-decision-status` error.
- **`design-intake` writes a `MANIFEST.md`.** The processed folder it creates lists the design page and the feature by path; a proposal without it is rejected with `intake_manifest_scope` or `intake_manifest_incomplete`, because every processed item has a manifest.
- **The intake skills, writing skills and guidance follow the new rules.** `po-intake` and `design-intake` take a `YYYY-MM-DD-slug` folder, label and link every claim, update a changed fact in place, and quarantine a contradiction with a `CONFLICT.md`; `po-specify`, the clarify skills, `design-handoff`, `dev-done`, `board-review` and `setup-project` name the labeling and current-state rule; `lint-wiki` lists the new findings; the root guidance and the Cursor wiki rule state the rules. The `feature new` generator creates a dated intake folder.
- **`log.md` is the only home for history, and every entry has one structured shape.** An entry is `## YYYY-MM-DD <operation> | <subject>` followed by `- paths:` (the changed paths), `- evidence:` (links to evidence, never copied evidence) and `- by:` (the actor), and at most one optional line of plain text. `SCHEMA.md` defines the format, states that the log is append-only, and states the rule for pages: a current-state page carries no date about itself, a date about the world stays in the page, and an ADR, an advisory review and each `## Reopen history` entry keep their own date as dated records. The board's entries use the format with `evidence: board preview <id>` and `by: <name> (<kind>)`, and keep the preview marker and the actor as HTML comments; a move's processed intake folder is listed under `evidence`. The skills, commands and the Cursor advisory rule that append to the log name the format, and `setup-project` appends its entry in it. The template `log.md` starts with no entry.
- **`SCHEMA.md` and `LIFECYCLE.md` start with front matter `schema-version: 1`.**
- **The status board has no date column.** `status-board.md` lists `| ID | Feature | Status | Owner | Board Review |`. The board renders, merges and reads only that header; a table with an `Introduced` column is refused as `invalid_status_board`, and lint reports it as `malformed-status-board`.
- **The feature status board is its own file, `status-board.md`.** `index.md` is now the general index of every page. The board service manages `status-board.md` exactly as it managed the status rows (merge by feature, `stale_status_row` and `duplicate_status_row`, recovery), the write role is `status-board`, and a proposal that supplies `status-board.md` is rejected with `managed_file`. A workspace needs `status-board.md` besides `index.md`, `SCHEMA.md` and `LIFECYCLE.md`, or the board stays read-only and lint reports `missing-required-wiki-file`. The lint codes of the status table are `malformed-status-board`, `feature-missing-from-status-board`, `status-board-missing-feature` and `status-board-frontmatter-drift`. The lifecycle skills, the guidance files and the Cursor rules read and update the status board row, and the packaged `wiki-*`, `feature-status` and `prep-sprint` skills read `status-board.md` for feature status.
- **A board transition writes no date.** `preview_transition` and `apply` change `status` and `owner` in the feature front matter and nothing else, and the lifecycle, clarify and design-intake checks no longer allow any date field. The packaged `po-specify`, `design-handoff` and `po-intake` guidance no longer asks for one.
- **The status board's "Recently updated wiki pages" report section is "Recently changed wiki pages"** and lists the paths of the newest `log.md` entries.
- **`AGENTS.md` is the single source of agent rules in a generated workspace, and `CLAUDE.md` imports it.** The root `CLAUDE.md` is the one line `@AGENTS.md`, and each platform folder (`backend/`, `web-user-app/`, `web-admin-portal/`, `mobile-android/`, `mobile-ios/`) repeats the pattern: its `AGENTS.md` holds the rules and its `CLAUDE.md` is `@AGENTS.md` plus the Claude Code skills and commands that no other tool shares. A platform `AGENTS.md` points at the root wiki workflow instead of restating it, and operations are named without a `/` or `$` prefix, with one section that gives the prefix of each tool. The platform `CLAUDE.md` skill lists name the skills as plain names: their `@.claude/skills/...` paths resolved relative to the platform folder and pointed at nothing.
- **The Cursor rules point at `AGENTS.md`.** `.cursor/rules/project.mdc` is the one always-on rule and references `@AGENTS.md`. The CLI read-surface and fallback rules that only `wiki.mdc` carried are in `AGENTS.md`. The scoped stack rules (`backend`, `web`, `mobile-android`, `mobile-ios`, `api-conventions`) and `advisory-review` stay.
- **`prism workflow install` writes the same layout for a new workspace.** `AGENTS.md` carries the connected-workflow section (with the knowledge-root paragraph for a knowledge root) and `CLAUDE.md` is `@AGENTS.md`. An existing `AGENTS.md` or `CLAUDE.md` is still preserved; the plan offers to add the `CONNECTED.md` pointer to `AGENTS.md` and `@AGENTS.md` to `CLAUDE.md`. The packaged workflow asset has a new digest, so existing board grants need to be issued again.
- **The board's pending-intake panel offers `ingest` next to `po-intake`,** and its card reads "awaiting intake".
- **`prism validate` and workspace detection look for `AGENTS.md`** where they looked for `CONTEXT.md`.
- **`sync-ai-context` checks the single-source layout.** It covers the import layout of `AGENTS.md` and `CLAUDE.md`, the scoped Cursor rules, and the `.claude/` and `.agents/` skill packagings, which cannot import each other.

### Removed

- **`introduced` and `last-updated` on feature pages, `introduced` on persona and business-rule pages and `date` on design pages.** The board rejects them as `unknown_frontmatter_fields`, lint reports them as `history-date-on-page`, and the formats, examples and lint's required fields no longer list them. The `invalid_last_updated` board error and the lint codes `invalid-feature-date`, `invalid-design-date`, `invalid-business-rule-introduced`, `invalid-persona-introduced` and `invalid-wiki-date` are gone with them.
- **The date-based `stale-page` warning.** Pages carry no date, so lint no longer reports page age from one. `stale-page` now derives a page's last verification from `log.md` (see Added).
- **`CONTEXT.md` in a generated workspace.** Its human overview (setup, repository layout and the operation names by tool) is in the generated `README.md`, and its operating rules are in `AGENTS.md`. `template/CONTEXT.md.jinja` and every reference to it are gone.
- **`.cursor/rules/wiki.mdc` in a generated workspace.** Its rules are in `AGENTS.md`, which `project.mdc` references.

## [0.4.0]

Release date: 2026-10-06

Prism 0.4.0 replaces the five fixed platforms with an application model that the workspace declares: `prism.workspace.yml` is `schema_version: 2` and lists repositories and apps, and features, lifecycle gates, status, the board and the graph read apps and their capabilities. The wiki schema is split into `SCHEMA.md` and `LIFECYCLE.md`. A workflow-only workspace can be a knowledge root that holds the shared wiki for apps in other repositories. Prism has no users of earlier versions, so workspaces created with 0.3.0 or earlier must be recreated; there is no upgrade path.

### Added

- **Knowledge-root workspaces.** `prism workflow install PATH --name NAME --knowledge-root` starts a workflow-only workspace with no apps that holds the shared wiki for apps living in other repositories, and records `workflow.purpose: knowledge-root` beside `workflow.mode: workflow`. The option belongs to `install`, starts a new workspace and cannot be combined with `--app`; register the external apps with `prism app add --repository … --remote …` and map their checkouts in `prism.local.yml`. The purpose is optional and has one valid value, and any other value (or a purpose on a generated workspace) is the error `invalid-workflow-purpose`. No gate reads it. `prism status` shows `Purpose: knowledge root` and says there are no features yet, `workspace.purpose` appears in `prism status --json`, `prism wiki lint --json`, the wiki queries and the graph (and `board.purpose` in the board's `discover`) for a knowledge root only, the board page shows a "no features yet" guide, and the installed `AGENTS.md` and `CLAUDE.md` describe the workspace as a knowledge root with the coordination contract for external repositories. The guidance comes from the "Connected board workflow" section of the root guidance templates through a `knowledge_root` condition (`knowledge_root_pointers` is new in the packaged workflow asset). With no features, with or without external apps, `prism wiki lint`, `prism validate`, `prism status`, `prism doctor --workspace` and the board pass; an external repository without a checkout is one warning. `docs/workspace-model.md` has the worked example and the README quickstart one line about it.
- **`prism presets` lists workflow presets.** The knowledge root is listed with its command under "Workflow presets", apart from the generation presets, and `prism presets --json` (new) returns `generation_presets` and `workflow_presets`.
- **`prism app list` and `prism app add`.** `prism app list [PATH] [--json]` shows the workspace's apps and repositories. `prism app add ID --stack STACK` previews, and with `--apply` (and `--yes` for automation) writes, one app in `prism.workspace.yml`, with `--name`, `--repository`, `--remote`, `--path`, `--audience`, `--has-ui` and `--serves-api`. It never generates code. `--remote` declares a new external repository together with its first app, an `other` app must declare both capabilities, and a path in this repository that does not exist yet is a warning. The manifest is validated before anything is written; any error writes nothing. The command says that the board identity changed, so a running board must be restarted and grants reissued.
- **The workspace model guide.** `docs/workspace-model.md` describes stacks and capabilities, repositories and `prism.local.yml`, apps and their fields, the `prism app` commands, workspaces with no apps and an example with one external repository.
- **`prism app retire`.** `prism app retire ID [--apply] [--yes] [--json] [PATH]` previews, and with `--apply` writes, `status: retired` on one app in `prism.workspace.yml`, with the same plan, confirmation and write checks as `prism app add`. It deletes no code, wiki page, requirement page or evidence, lists the features before `done` that still name the app, and says that the board identity changed (restart the board and reissue grants). An unknown or already retired app is an error that writes nothing. A retired app stays in `prism app list`, status, the board's apps and the graph, marked `retired`.
- **Retired apps in feature scope.** A retired app stays valid in the `apps` of a feature that is `done`. A feature before `done` that still names it is flagged `app-retired-in-scope`: lint reports an error and every lifecycle action on that feature is blocked with that code until its `apps` is edited explicitly (retirement never changes scope by itself). A new feature, or an edit that adds a retired app to a scope, is rejected with `app-retired` (`app_retired` on the board; `app_retired_in_scope` for a lifecycle proposal on a flagged feature). Adding an app never changes an existing feature's `apps`.
- **API work needs an app that serves an API.** When a feature's `## API surface` declares API work, at least one active app in its `apps` must have `serves-api` (`unknown` counts as true). Lint reports `api-surface-without-api-app` for features before `done`, the `design-handoff`, `dev-start` and `dev-done` transition checks block with that code, and the board rejects a `design-handoff` proposal with `api_surface_without_api_app`.

### Changed

- **`min_prism_cli_version` follows the package version.** A manifest written by `prism new`, `prism update` or `prism workflow install` names the running CLI's version as its minimum, and the template renders that value from the version the CLI passes to Copier. A Copier run without the CLI names no minimum (`0.0.0`). During `prism update` the saved template renders with the version recorded in the manifest's `generated_by`, so an unedited minimum advances with the template and an edited one is reported as a competing edit.
- **The packaged skills require `prism-kit>=0.4.0`.** The wiki, lint, status and sprint-preparation skills and the Cursor wiki rule use commands that 0.4.0 introduced, so their CLI probe accepts `prism 0.4.0` or newer.
- **`prism.workspace.yml` is now `schema_version: 2`, and earlier manifests are not supported.** The manifest lists `repositories` (the workspace itself needs no entry; each other repository has a canonical `remote`), `apps` (an ID, a name, a `stack` from the registry, a `repository`, a repository-relative `path`, an optional `audience`, `status` and capability overrides) and `app_maturity` keyed by app ID. `project.platforms` and `platform_maturity` are gone. A version-1 manifest is refused with `unsupported-workspace-manifest-schema`; recreate or reinstall the workspace with this CLI. `prism new`, `prism workflow install` and `prism update` write version 2: the questionnaire's platforms and the `--app` choices become apps (ID, matching stack, default directory, repository `workspace`). On a workspace that already declares apps, `--app` may only name those same apps; register another with `prism app add`.
- **One normalizer reads the manifest.** The new `prism_cli/app_model.py` holds the stack registry (`spring-backend`, `nextjs-web`, `android-compose`, `ios-swiftui`, `other`, with the `has-ui` and `serves-api` capabilities) and validates repositories and apps with stable error codes. Workspace inspection, status, the board service and its identity, workflow install and `prism update` all read the manifest through it. An external repository without a checkout in the untracked `prism.local.yml` is one `external-repository-unresolved` warning, never an error.
- **Workspace output reports `apps` instead of `platforms`.** The `workspace` object of `prism status --json`, `prism wiki lint --json`, the wiki query commands and the graph, and the `board` object of the board's `discover`, list every app with `id`, `name`, `stack`, `repository`, `path`, `audience` (or `null`), `status`, `capabilities` (`has-ui` and `serves-api`, each `true`, `false` or `"unknown"`) and `maturity` (the `app_maturity` entry or `null`). `workspace.platforms`, `workspace.platform_maturity` and `board.platforms` are gone. `prism status --json` also reports `workspace.repositories` (`id`, `remote` and, for an external repository, `checkout` as `resolved` or `unresolved`, never the local path). The packaged JSON schemas describe the new shape. `prism status` and `prism doctor --workspace` show an apps table (ID, name, stack, repository, path, status, maturity) and one line per external repository, and the board page's workspace summary and generated prompts say "apps" and list their IDs.
- **MCP tool contract 3.** `discover` and `list_skills` report `"mcp_contract": 3` because `discover` returns `board.apps` where it returned `board.platforms`. The server instructions and the `discover` tool description mention the apps.
- **`--platform` is now `--app`.** `prism workflow install` and `prism workflow upgrade` take `--app` with the five generated app IDs, and `--platform` is removed. The plan and receipt list `apps` instead of `platforms`. A new workspace installed without `--app` has no apps instead of failing. The questionnaire, presets and `prism new` keep their `platforms` answer.
- **Doctor decides relevance by stack.** The Docker, JDK and Xcode checks are keyed by the stacks `spring-backend`, `android-compose` and `ios-swiftui` of the workspace's active apps in this repository, or of a preset's platforms. The checks that run for the five generated apps and a preset are the same as before.
- **A workspace with no apps is served with writes enabled.** The board no longer treats an empty app scope as read-only (the "explicit nonempty app scope" requirement is gone; a missing project name now gives "A project name is required."). Operations that need an app scope still stop at their own check, and the rejection says that the workspace declares no apps and points to `prism app add`.
- **`prism.local.yml` is ignored by git.** The generated project's `.gitignore` lists it, and `prism workflow install` adds the rule to an existing `.gitignore`.
- **`dev-done` needs release evidence or a delivery attestation per app.** The `Release` cell of each delivery evidence row must be `release: <reference>`, `tag: <reference>` or `deployment: <reference>` (the URL of, or a workspace path to, a release, tag or deployment record), or `attested by <Name>: <reference>` (a URL or path to what the person checked). The prefix is matched without regard to case. A bare commit SHA, a pull-request or merge-request URL, `merged`, a branch name, free text or a placeholder is rejected with `release-evidence-required`, because a commit or pull request proves which code changed, not that it shipped. Lint applies the rule to `done` features, the `dev-done` transition check reports it as the check `release-evidence-required`, and the board rejects a `dev-done` proposal with `release_evidence_required`. - `prism board serve` reports a client's reset connection (`ConnectionResetError`) with one quiet line instead of a traceback each time.
- `prism new` without `--template` ends with one message and exit code 3, instead of a Copier traceback and exit code 5, when the template release tag that matches the installed version is not published. The message points to `--template <path or URL>` or a released version.
- `prism doctor --workspace .` in a generated project suggests `prism workflow upgrade` for a missing workflow pin, because `prism workflow install` refuses generated workspaces.
- `prism doctor`, run without a target inside a workflow or generated workspace folder, points to `prism doctor --workspace .` instead of saying that you can generate a project.
- `prism board serve` flushes its banner lines, so a pipe or a log file shows the board URL while the service runs instead of only at exit.
- The board shows the new stage right after an apply or a recovery, because the board snapshot is refreshed before the operation answers.
- A live update that arrives before the apply response no longer replaces "Operation applied" with a stale-preview warning.
- An apply rejected because its sources changed shows the service's reason and a **Preview again** action, instead of an "outcome unknown" operation that was never created. An apply after the session expired shows the expiry message and **Reconnect**.
- After the board service restarts, the page shows "Board session expired · Reconnect" instead of staying STALE.
- `prism board serve` stops promptly on Ctrl+C while a browser is connected.
- Dropping a card on a column that does not accept it explains why, also to screen readers.
- Every board dialog keeps keyboard focus inside it, including Shift+Tab from the heading, and the header no longer scrolls sideways at tablet width.
- Generated web apps no longer describe themselves as based on another application.
- Generated Android app: a first-launch crash from the welcome-slide drawables, a nonexistent instrumentation runner and instrumentation test names that failed dexing.
- Generated web apps: the Microsoft provider ID is `microsoft-entra-id`, and a rejected backend refresh ends the web session.
- `docs/cli-release.md` points to the current acceptance record.
- **A write path Windows cannot hold is rejected at preview.** A path segment that contains `:` `<` `>` `"` `|` `?` `*` or a control character, ends in a dot or a space, or is a reserved device name (`CON`, `NUL`, `COM1` and the others, with or without an extension) is rejected with `invalid_path` on every operating system. Before, a path such as `F-001-document-review.md:stream.md` passed preview, and apply failed partway through, left the workspace half written and kept the operation unresolved.
- **`feature-reopen` archives every delivery-evidence table that `dev-done` accepts.** Both now read the table with one parser, so column order, header case, emphasis in the header and the case of the platform ID no longer decide. Before, a feature completed with a reordered table or a capitalised platform could never be reopened through the board. The reopen record still has to repeat each prior row verbatim, in the table's own column order.
- **A resolved answer is matched as whole words in the clarify skills.** The traceability check no longer accepts `no` inside `not`, `know` or `notice`; case and whitespace are still ignored.
- **`changes` and `query` no longer drop an item larger than one result.** An oversize event is returned in chunks (`event_chunk`, continued with the cursor `N~K`), and an oversize `query` item is replaced by an entry that names it and says to read its path with `read_workspace`. Before, the cursor moved past it and a client never saw it.
- **HTTP Bearer clients can page.** `POST /api/board/v1/workspace/read` and `POST /api/board/v1/query` accept an optional string `cursor` and return `next_cursor`, as the MCP tools do.
- **An intake proposal can no longer link the pending folder it moves.** `po-intake` wrote `sources: [knowledge/intake/pending/<folder>]` on a new feature page while the same proposal moved that folder to `knowledge/intake/processed/<folder>`, so the page linked a folder that no longer existed and the next agent stopped because it could not read its source. A new `sources` entry (a feature's `sources`, a persona's `sources` or a business rule's `source`) that lies under `knowledge/intake/pending/` is now rejected with `intake_source_not_processed`, and one that will not exist once the proposal applies with `source_link_missing`; both carry `details` and the first names the processed path to list. A path counts as existing when it is on disk, is written by the proposal or is inside the processed folder the proposal's own move creates. An entry that is already on the page, a URL and a persona or business-rule entry that is not a `knowledge/` path are not checked, so an older stale link does not block an edit.
