# Changelog

All notable changes to Prism are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- **Two-layer generation and the first stack pack.** One `copier.yml` and one template tag cover two layers, chosen by the hidden question `prism_layer`: the workspace layer (`template/`: the knowledge base, the guidance, `shared/`, `docker-compose.yml` and the manifest) and one app layer per scaffolded app (`packs/<stack>/`), which Copier applies to the repository root with every path under `{{ app_path }}/` plus the app's workflow `.github/workflows/<id>.yml` and Cursor rule `.cursor/rules/<id>.mdc`. Each app keeps its own answers in `<path>/.copier-answers.yml`, so one template applies several times to one project. `packs/spring-backend/` is a minimal, real pack: a Spring Boot app with a health endpoint (`GET /api/health`), a context test and a MockMvc test, its Gradle wrapper, Dockerfile, task file, guide, `AGENTS.md`, CI workflow and Cursor rule, all scoped to the app's path.
- **`packs/versions.yml`, the one place that pins versions.** A pack reads its stack's baseline through the `versions` question (`java`, `kotlin`, `spring_boot`, `spring_dependency_management`, `gradle`, `mockk` and `postgres` for `spring-backend`; the workspace's `docker-compose.yml` and the tests read the same `postgres` tag), and the workspace guidance reads the same pins. A test fails when a pack file hard-codes a version that `versions.yml` pins.
- **Derived identifiers and a remembered port for every scaffolded app.** From the app's ID the CLI derives the package segment (the ID without hyphens, which must pass the `package_identifier` rules and be unique across the workspace's apps, so `my-app` and `myapp` collide), the package and its directory, the module name (PascalCase), and the CI workflow name and `paths:` filters scoped to the app's path. It picks the first free port of the stack's range (`spring-backend` from 8080) when the app is added and stores it in the app's answers; removing another app never shifts it. An app ID or path that would replace a file of the workspace layer (`api-contracts`, a path inside `docs/`, `knowledge/`, `shared/` or `.github/`) is refused.
- **`prism app add --scaffold`.** It generates a new app into an existing generated workspace, at the template revision the workspace records, not the CLI's version or the latest tag. With `--apply` it works on the branch `prism-scaffold-<id>` with one commit per layer: the workspace layer is brought in line with the new app list (compose service, task include, guidance), then the app is generated and recorded in the manifest. It needs the workspace to be its own git repository with a clean tree, and `--trust-template` for a custom template. The preview shows the plan (`scaffold` and `notes` in the JSON).
- **The `spring-backend` slice and its fail-closed local development identity.** A generated backend app is one compiling vertical slice with its tests: the `users` entity with its Flyway migration, a repository, a service and the controller of `GET /api/me`, the shared error model (`ApiException`, the built-in exceptions and `GlobalExceptionHandler`), an OAuth2 resource-server configuration and the dev identity. `POST /api/dev-identity/token` exists only under `@Profile("local")`, answers loopback requests only (a non-loopback peer, a forwarding header or a non-loopback host name is refused), and signs a 15-minute JWT (`iss=prism-dev-identity`) with an RSA key generated in memory at startup and never written to disk. Startup fails when `local` is active together with a configured identity provider (`DevIdentityGuard`). With no identity provider configured the app rejects every token. No JWT secret exists anywhere in the template, the generated `docker-compose.yml` sets no profile, and the `dev` task sets `local` explicitly. The slice has no example business features: no transactions, no OAuth providers.
- **Tests of the slice, with Testcontainers.** The integration tests boot the default profile (the token route answers 404) and `local` (sign in, then `GET /api/me`) against a PostgreSQL started by Testcontainers, so `./gradlew test` needs Docker and no credentials and never touches the development database; further tests cover the startup failure, the loopback policy, the token, the service, the error model and the OpenAPI contract. The app's workflow runs `./gradlew build` on a clean runner with no secrets.
- **Tasks for the local database and the dev identity.** `task db-up` and `task db-down` start and stop the workspace's PostgreSQL, and `task <app-id>:dev` runs the backend with the `local` profile. Each backend keeps its tables in its own schema (`DATABASE_SCHEMA`), so several backends share the workspace database.
- **A README and entity docs in every backend app.** The pack generates `README.md` (the commands, the dev identity's limits) and `docs/entities/` (the template and the `users` entity).
- **The manifest field `generation`.** Each app is `scaffolded` (Prism generated its code, so `prism update` keeps it current) or `registered` (the default). Only an app of a generated stack in the workspace repository can be scaffolded; anything else is `invalid-app-generation`.
- **Conflicts are reported per layer.** After each layer `prism update` scans for `.rej` files and conflict markers, and a conflicted update exits with 6.

- **The `nextjs-web` pack: one web stack, any number of web apps.** `packs/nextjs-web/` generates a Next.js (App Router, TypeScript) app at its own path, once per web app, with one vertical slice and its tests and no example business features:
  - a sign-in page labelled "Local development sign-in" and a route handler (`POST /api/session`) that asks the backend's dev identity (`POST /api/dev-identity/token` of the shared OpenAPI contract) for a token and keeps it in an httpOnly cookie, and `DELETE` removes it; the token is never returned in a body, and sign-in and sign-out accept same-origin requests only;
  - one page that shows `GET /api/me`, read from the server through a typed client that `openapi-typescript` and `openapi-fetch` generate from `shared/api-contracts/openapi.yml` (`npm run generate:api`, run before `dev`, `build`, `lint`, `typecheck` and `test`), so a path or field the contract lacks fails the typecheck;
  - Vitest and Testing Library tests of the sign-in route handler (cookie set, httpOnly, same-origin, failure cases), the sign-in page, the profile page with a mocked client and the client itself;
  - a committed `package-lock.json` so `npm ci` installs the same packages everywhere, a Taskfile, a README, `docs/guide.md`, `AGENTS.md`, a `CLAUDE.md` that imports it, a Cursor rule, and a CI workflow that runs `npm ci`, lint, typecheck, test and build on a clean runner.
  The `audience` of an app is display text only: no route, check or permission reads it. Each web app gets its own port (3000, 3001, ...), package name, session cookie name, workflow and display name from its ID. The sign-in is a local development identity and never presents itself as complete authentication.
- **Web versions are pinned in `packs/versions.yml`.** Node, Next.js, React, TypeScript, ESLint and its Next.js configuration, the API client generator and the test tooling (Vitest, Vite, jsdom, Testing Library) have one baseline. `scripts/refresh-nextjs-web-lock.py` rewrites the pack's lockfile from the pins, and a test fails while the lockfile, `package.json` and the pins disagree or the lockfile lacks the native packages of another platform.
- **A `web-conventions` skill** for the generated web apps (`.agents/skills/` and `.claude/skills/`, shipped when a `nextjs-web` app exists): the slice, the generated client, the session cookie, the tests and how to replace the dev identity, citing slice files by path; a test checks that every cited path exists in the pack.
- **The shared contract defines the dev identity and `/api/me`.** `POST /api/dev-identity/token` (`x-prism-dev-only`, no security) and `GET /api/me` (bearer JWT) (`createDevToken` and `getMe`); the token request body is optional (`email`, `displayName`) and the profile has `id`, `displayName`, optional `email` and `createdAt`.
- **One source for every skill, command and Cursor rule.** `template-skills/<name>/skill.md` holds a skill's name, its one description, the layers it ships to (Codex skill, Claude command, Claude skill, Cursor rule), the stacks it applies to, the per-host fields and one body. `scripts/build-skill-layers.py` renders `template/.agents/skills/`, `template/.claude/commands/`, `template/.claude/skills/` and `template/.cursor/rules/` from it, copies each skill's `references/` into both skill folders and writes the stack conditions into the generated block of `_exclude` in `copier.yml`. `--check` fails when a generated file differs from its source, and a test fails when a layer file is edited without its source. Another test renders a workspace with all four default apps and with one app and checks how Codex, Claude Code and Cursor each discover the skills, that no layer file is an orphan and that every skill the guidance names exists in the layer it names.
- **A `deployment` skill in every generated workspace.** `.claude/skills/deployment/` and `.agents/skills/deployment/` explain how to deploy each generated stack and hold the former scripts and configuration as worked examples under `references/`: the Azure Container Apps scripts and guide (`references/azure/`, `azure-setup.md`) for a backend app, the Cloudflare Workers through OpenNext guide and the Wrangler, OpenNext and preview-variable files (`references/cloudflare/`, `cloudflare-setup.md`) for web apps, and `mobile-store-release.md` for the tag-triggered store release jobs that the mobile workflows no longer carry. Each guide includes the GitHub Actions deploy job that the generated workflow used to hold. The skill states that the user and their agent own the cloud choice, the secrets and the deployment, and that the files are a worked example for one choice. The Codex layer adds `agents/openai.yaml`. The skill is a stack skill like `spring-boot-conventions`, not one of the 26 canonical workflow skills, so the packaged workflow asset and its digest do not change.
- **The `android-compose` pack: one Android stack, any number of Android apps.** `packs/android-compose/` generates a Kotlin and Jetpack Compose (MVVM) app at its own path, once per Android app, with one vertical slice and its tests and no example business features:
  - a "Local development sign-in" screen and a profile screen with their state holders (`SignInViewModel`, `ProfileViewModel`): signing in calls the shared contract's `createDevToken` (`POST /api/dev-identity/token`) and opens an in-memory session, and the profile screen shows `getMe` (`GET /api/me`) with the bearer token; a rejected token returns to the sign-in; the token is never logged, persisted or put in a `toString()`, and the client adds no HTTP logging;
  - a hand-written Retrofit and kotlinx.serialization client behind one `ApiClient` interface, and `ApiContractTest`, which reads `shared/api-contracts/openapi.yml` and fails when the routes, the DTO fields or the bearer security of `getMe` differ;
  - 34 JVM unit tests: both state holders against a fake client, the client against a MockWebServer, the contract check and a Compose UI test of the sign-in screen under Robolectric that asserts the label "Local development sign-in", so CI proves them without an emulator;
  - the Gradle wrapper, a Taskfile (`build`, `test`, `lint`, `reverse`, `install`), a README, `docs/guide.md`, `AGENTS.md`, a `CLAUDE.md` that imports it, a Cursor rule, and a CI workflow that runs `./gradlew assembleDebug testDebugUnitTest` on a clean runner.
  Each Android app gets its own application ID and namespace (`<package_identifier>.<app ID without hyphens>`), package directories, Gradle project name, workflow and display name from its ID, so two Android apps of one workspace never share one.
- **A local backend flow for the dev identity that keeps its loopback guard.** The backend answers the dev identity to loopback requests only, so the Android app calls `http://localhost:8080/` (`apiBaseUrl` in the app's `gradle.properties`, overridable with `-PapiBaseUrl=`) and `adb reverse tcp:8080 tcp:8080` (`task <app-id>:reverse`) carries that to the host, from an emulator and from a USB device. `10.0.2.2` and LAN addresses are refused by the backend and are not allowed by the debug network security config; debug builds allow cleartext HTTP to `localhost` only, and a release build refuses an `apiBaseUrl` that is not `https://`.
- **Android versions are pinned in `packs/versions.yml`.** The Android Gradle Plugin, Kotlin, Gradle, the JDK, the SDK levels, the Compose BOM and the library and test versions have one baseline that the pack reads.
- **The Android skills describe the slice.** `android-conventions`, `android-contract-alignment`, `android-feature-delivery`, `android-testing`, `android-build-verify` and `compose-design-system` cite the slice's files by path, list the workspace's Android apps from the app list, and explain how to replace the dev identity with an identity provider.
- **The `ios-swiftui` pack: one iOS stack, any number of iOS apps.** `packs/ios-swiftui/` generates a SwiftUI app at its own path, once per iOS app, with one vertical slice and its tests and no example business features:
  - a sign-in screen labelled "Local development sign-in" that asks the backend's dev identity (`POST /api/dev-identity/token` of the shared OpenAPI contract) for a token, and a profile screen that shows `GET /api/me`, each with its `@MainActor @Observable` view model, built for Swift 6 strict concurrency;
  - a `URLSession` API client kept to the contract's two operations (`createDevToken` and `getMe`, the bearer token on `getMe`), whose paths the template validation checks against `shared/api-contracts/openapi.yml`, and a token kept in memory only, never logged;
  - XCTest unit tests of both view models with a fake client and of the client's request building and response reading, one XCUITest of the sign-in screen that waits until an element is hittable and allows 30 seconds per screen, an XcodeGen `project.yml`, a Taskfile, a README, `docs/guide.md`, `AGENTS.md`, a `CLAUDE.md` that imports it, a Cursor rule, the Fastlane TestFlight lane, and a CI workflow that generates the project with XcodeGen, builds for a simulator and runs the tests on `macos-latest`.
  Each iOS app gets its own module, target, scheme, Xcode project name, bundle identifier (`<package identifier>.<app ID without hyphens>`), workflow and display name from its ID, and its `audience` is display text only. The dev identity works in the simulator only: the backend serves it to loopback requests, the simulator reaches a backend on the Mac as `localhost`, and a physical device is refused with a message that says so. It is not complete authentication. Swift, Xcode and the iOS deployment target are pinned in `packs/versions.yml`. Only the macOS CI job builds and tests the pack, so the iOS maturity stays `experimental`.

### Changed

- **`prism new` collects an app list; Copier no longer asks about platforms.** The questionnaire has project identity, the apps (an ID, a stack, a path, an audience, a repository and whether to scaffold or only register each), auth methods and the GitHub owner. A preset is an app list, an answers file carries `apps` (leaving it out is an error; `apps: []` generates the workspace layer alone), and the interactive flow asks for the apps and then for further apps. The CLI runs the workspace layer with the stacks and the app list as data, then each scaffolded app's pack with its own answers file. An app of an external repository or of the `other` stack is registered, never scaffolded.
- **The backend is generated by the `spring-backend` pack.** A backend app gets the pack's slice at its own path, with its own package, port, workflow and Cursor rule, and the workspace's `docker-compose.yml` has one service for each backend app, with the database settings of the container and no Spring profile. The workspace layer no longer renders the full backend sample.
- **The API contract is the auth contract.** `shared/api-contracts/openapi.yml` defines `POST /api/dev-identity/token` (tagged `x-prism-dev-only`) and `GET /api/me` with bearer JWT security, served at `/api/...`. The contract no longer depends on the `auth_methods` answer, and `docs/api/conventions.md` and the Cursor API rule describe it. Template validation checks the contract, and the web client is type-checked against it by the `nextjs-web` pack's `generate:api` and `typecheck`; it no longer compares the clients of the Android and iOS samples with it until their packs replace them.
- **The backend skills describe the slice.** `spring-boot-conventions`, `testing-patterns`, `error-handling`, `endpoint`, `add-endpoint`, `backend-feature-delivery`, `create-migration`, `document-entity`, `migration-conventions` and the others cite the slice's files by path, and `security-auth` explains the dev identity's guards and how to replace it with a real identity provider. The Azure example of the `deployment` skill passes the identity provider's issuer instead of a JWT secret and OAuth provider secrets.
- **`prism update` works on a branch, one commit per layer.** It creates `prism-update-<template tag>`, updates the workspace layer and commits, then updates each active scaffolded app from its own answers file and commits after each one, reports every layer, and stops before merging when any layer conflicted. Without conflicts the branch stays checked out for you to review and merge; the changes no longer land uncommitted on your branch. The clean-tree precondition, the baseline checks and the field-level manifest merge stay. A recopy follows the same branch flow and keeps the workspace's apps and repositories when it renders the manifest again. The manifest render resolves the workspace layer root explicitly.
- **Copier's own answers file stays as Copier wrote it.** For a remote template `prism new` and `prism update` no longer rewrite `.copier-answers.yml`, so a later update does not see a difference to merge.
- **Generated CI and the template validation generate through the CLI.** `template-validation.yml` and `scripts/validate-template.ps1` generate with `prism new` (a preset or an answers file) from the checkout instead of raw `copier copy --data platforms=...`, and the backend job builds and tests the pack's app.
- **A skill's condition names stacks, not platform IDs.** The `platforms` and `reference-platforms` front matter of `template-skills/*/skill.md` are `stacks`, `reference-stacks` and `reference-apps`, and the generated `_exclude` block tests `stacks` and `app_ids`.
- **The default web app is `web`.** The default app IDs are `backend`, `web`, `mobile-android` and `mobile-ios`; `web-user-app` and `web-admin-portal` are no longer IDs Prism knows and stay valid only as IDs you choose. The `backend-web` preset is `backend` and `web`. A second web app is one more `nextjs-web` entry in the app list (`admin`, audience `internal`, for example) or `prism app add admin --stack nextjs-web --scaffold`; `web` is no longer a reserved app ID. The interactive flow asks for the audience of a web app.
- **`generate-clients` covers the web apps through their own scripts.** `task generate-clients` calls each web app's `generate-api` task (`openapi-typescript`) instead of generating a TypeScript Axios client into `shared/generated/`; the root `task lint` and `task test` run lint, typecheck and the tests of every web app.
- **The Cloudflare deployment example is one set of files for every web app.** `references/cloudflare/wrangler.jsonc` and `dev.vars.example` replace the per-sample files, hold only `API_BASE_URL` (the web apps read no other variable and keep no secret of their own), and the guide lists each web app with its Worker name. The OpenNext build and `wrangler deploy --dry-run` of a generated web app pass with the pins in the guide, and the web apps need no `webpack` hook for it. The Azure example sets no CORS origin for the web apps, which call the backend from their servers.
- **The workspace layer documents web apps from the app list.** The root `README.md`, `AGENTS.md`, `Taskfile.yml`, `docs/ai-agents.md`, `docs/architecture.md` and `docs/deployment/ci-cd.md` list each `nextjs-web` app by its path, port and workflow, and a web app's `.gitignore` is its own.
- **A skill has the same text in every tool.** A workflow skill that was both a Codex skill and a Claude command now has one body: the command's detailed workflow with the skill's rules, output and stop conditions. The backend and platform skills that were in both `.claude/skills/` and `.agents/skills/` have one text each, the more complete of the two (`testing-patterns`, `spring-boot-conventions`, `security-auth`, `error-handling`, `android-conventions`, the `ios-conventions` references and others), and `board-review` shares one body with its Cursor rule. The host differences are the invocation (`$name` in Codex, `/name` in Claude Code) and a few marked lines. The packaged workflow asset has a new digest because the canonical skill text changed.
- **Cursor rules carry a `description`, and generated front matter is valid YAML.** Every `.cursor/rules/*.mdc` has a `description` and either `globs` or `alwaysApply`; Claude skill `argument-hint` values such as `[variant] [adb-serial]` and descriptions that contain a colon are quoted.
- **`wiki-query` and `design-handoff` read cleanly.** The `wiki-query` match classes sit under their own heading, and the numbered steps of `design-handoff` have no gap.
- **The questionnaire asks for project identity, platforms, auth methods and the GitHub owner.** The `database`, `supporting_services`, `use_docker`, `cloud_provider` and `web_hosting` questions are removed, with their presets, defaults, answers-file validation, advanced prompts, summary lines, manifest fields (`project.database` and the others) and template conditions. A backend app always comes with the PostgreSQL development database in `docker-compose.yml`; the backend skills describe PostgreSQL only. `prism new` rejects an answers file that sets a removed question with an "Unknown answer(s)" error; Copier itself ignores a `--data` value for a question it does not have.
- **Generated CI builds and tests only.** The backend workflow no longer pushes an image or deploys to Azure, the web workflows no longer build the Cloudflare bundle, run a Wrangler dry run or deploy, and the Android and iOS workflows no longer run on `v*` tags or release to the Play Store or TestFlight. No generated workflow reads a secret.
- **Web apps build and test without hosting files.** `wrangler.jsonc`, `open-next.config.ts` and `.dev.vars.example` are no longer generated, and the `@opennextjs/cloudflare`, `wrangler` and `esbuild` dependencies and the `build:cloudflare`, `preview` and `deploy` scripts and tasks are removed from the web apps. The web `.gitignore` entries for `.open-next/` and `.dev.vars*` are gone; the skill lists the lines to add when you adopt the Cloudflare example.
- **Deployment docs point to the skill.** The generated README, `AGENTS.md`, `docs/README.md`, `docs/architecture.md`, `docs/deployment/ci-cd.md`, the web guides, the Cursor rules and the wiki index no longer describe a hosting target and name the `deployment` skill instead. The web app maturity caveat in `prism.workspace.yml` says that the apps are verified by lint, typecheck, tests and build, with a mocked backend.
- **`deploy-device` ships with an Android app and covers each one.** It lists every Android app with its folder and application ID, runs `adb reverse` before installing, and no longer ships to an iOS-only workspace.
- **An Android app's client is hand-written, not generated.** `task generate-clients` no longer generates a Kotlin client into the Android app; the app's `ApiContractTest` fails when its client and the contract disagree, and `scripts/validate-template.ps1` matches the paths of every `ApiService.kt` against the contract.
- **The workspace layer documents Android apps from the app list.** The root `README.md`, `AGENTS.md`, `Taskfile.yml`, `docs/ai-agents.md`, `docs/architecture.md` and `docs/deployment/ci-cd.md` list each `android-compose` app by its path and workflow, the root Taskfile includes each app's tasks, and an Android app's `.gitignore` is its own.
- **The mobile store release note describes Android without Fastlane.** The `deployment` skill's note builds a signed bundle with `-Pandroid.injected.signing.*` and an `https://` `apiBaseUrl`, and uploads it with a publishing action or a `supply` lane you add; the pack ships no signing, lane or release job.
- **The iOS skills describe the slice.** `ios-conventions`, `ios-build-verify`, `ios-contract-alignment`, `ios-feature-delivery`, `ios-testing` and `swiftui-design-system` cite the slice's files, name each iOS app's tasks (`task <app-id>:build`, `:test`) and explain how to replace the dev identity; their references on SwiftData, navigation, token refresh and the design-token components are gone. `generate-clients` no longer generates a Swift client: the iOS client is hand-written and kept to the contract.
- **The workspace layer documents iOS apps from the app list.** The root `README.md`, `AGENTS.md`, `Taskfile.yml`, `docs/ai-agents.md`, `docs/architecture.md` and `docs/deployment/ci-cd.md` list each `ios-swiftui` app by its path and workflow, and the root `.gitignore` carries no iOS section because each app ignores its own build output.
- **The macOS `ios-build` job builds and tests two iOS apps.** It generates a backend and two iOS apps (the second at `apps/partner-ios`) through `prism new`, commits and clones the result, runs XcodeGen, builds each app for a simulator, checks the built `API_BASE_URL` and runs each app's tests. The generated iOS workflow no longer pipes `xcodebuild` through `xcpretty`, which the runner does not have.

### Removed

- **The full backend sample (`template/backend`).** Its authentication (passwords, refresh tokens, Google, Apple, Facebook and Microsoft OAuth), its transactions module, its examples and docs, its H2 test profile, its springdoc setup and its per-stack `_exclude` entry are gone; the pack's slice replaces it. The Hygen generators under `_templates/` still target the old layout until they are removed.
- **The two web samples and everything that only served them.** `template/web-user-app/` and `template/web-admin-portal/` (NextAuth, next-intl, Tailwind, the `/api/v1` proxy, the dashboard and admin shells and the OAuth sign-in), their workflow templates, the `web.mdc` Cursor rule source `template-skills/cursor-web/`, the Hygen `page` generator, `scripts/check-web-auth.mjs`, the `NEXTJS_WEB_FULL_SAMPLE` switch of `prism_cli/packs.py`, the per-sample Wrangler and preview-variable references, and the template validation's assertions about them.
- **The JWT and OAuth variables of `.env` and `.env.example`, the OAuth operations and the transactions operations of the API contract, and the JWT and OAuth provider secrets of the Azure example.** The template holds no JWT secret.
- **The `platforms` question and answer.** `prism new` rejects `platforms` as an unknown answer, `copier.yml` has no such question, and the generated manifest template no longer renders apps; the CLI records them.
- **The per-stack Cursor rule source `template-skills/cursor-backend/` and the workspace workflow `backend.yml.jinja`.** The backend's rule and workflow belong to its pack, per app.
- **The always-on Cursor rule `.cursor/rules/project.mdc`.** Cursor reads `AGENTS.md` itself, so a rule whose only content was `@AGENTS.md` loaded the same text twice.
- **The generated `infra/azure/` scripts, `backend/docs/azure-setup.md`, `docs/deployment/cloudflare-setup.md` and the root `infra:*` tasks.** They moved into the `deployment` skill's references. The `.gitignore` block for Azure credential files moved into the Azure guide.
- **Redis support.** The Redis service in `docker-compose.yml`, its `.env` and `.env.example` variables and every Redis step of the Azure scripts are removed.
- **The `prism validate` requirement for `docs/deployment/cloudflare-setup.md`** and the "live Cloudflare deployment" warning of `prism new`.
- **The full Android sample (`template/mobile-android`) and everything that only served it.** Hilt, Room, DataStore, the Credentials API sign-in, the welcome, social and example screens, the transactions client, Fastlane, `local.config.properties` (and its `_skip_if_exists` entry), the sample's eight docs, its workflow template, its `_exclude` entries, the Android Hygen templates, the `.gitignore` block, the Cursor rule source `template-skills/cursor-mobile-android/` (the pack carries the rule per app), the `ANDROID_COMPOSE_FULL_SAMPLE` switch and its row in `full_sample_apps()`. The pack's slice replaces it; `mobile-android` stays the default ID and path of an Android app.
- **The full iOS sample (`template/mobile-ios`).** Its login with OAuth and password forms, repositories, Keychain token storage, SwiftData cache, transactions example, theme, `Config/*.xcconfig` files and docs are gone; the pack's slice replaces them. The `IOS_SWIFTUI_FULL_SAMPLE` switch, the sample's `_exclude` and `_skip_if_exists` entries, its workflow template, the Cursor rule source `template-skills/cursor-mobile-ios/`, the iOS Hygen generators under `template/_templates/` and the iOS rules of the root `.gitignore` are removed with it. `mobile-ios` stays the ID of the default iOS app, and another app of the `ios-swiftui` stack can now be scaffolded at any path.
- **No full sample remains.** All four stacks (`spring-backend`, `nextjs-web`, `android-compose` and `ios-swiftui`) are packs and the workspace layer renders no app code. `full_sample_apps()` and the sample branches of the scaffold checks are gone from `prism_cli/packs.py`, so a stack without a pack (`other`) is refused with one message, `$ClientsWithoutPack` is removed from the template validation (the hand-written Android and iOS clients are both path-matched against the contract), the Hygen `screen` generator is deleted because its only platforms were the two samples, and the skill generator drops the `reference-apps` front-matter key that only a full sample used.

## [0.5.0]

Release date: 2026-10-06

Prism 0.5.0 turns the wiki into a knowledge base with one rule for time: a current-state page says what is true now, and `log.md` is the only home of history, in one structured entry shape. Claims carry evidence labels (Decided, Observed, Proposed, Assumed, Unknown) and link their evidence; decisions are records that are superseded rather than rewritten, with the pages that relied on them updated in the same operation. Raw sources are dated, immutable folders (`YYYY-MM-DD-slug/`) with a manifest, and a source that contradicts a page is quarantined with a `CONFLICT.md` until a human resolves it. The wiki has new page kinds (topics, research, plans, `direction.md` and `roadmap.md`), a generic `ingest` skill that writes any of them for any role, a general `index.md` that lists every page, and a separate `status-board.md` for feature status. `AGENTS.md` is the single source of agent rules in a generated workspace, and `CLAUDE.md` and the Cursor rules import it. `prism wiki lint` checks links, `sources` entries, `repo:` links into other repositories and page freshness from the log, and `prism wiki verify` records a verification. Prism has no users of earlier versions, so workspaces created with 0.4.0 or earlier must be recreated; there is no upgrade path.

### Added

- **Page kinds beyond the feature pipeline.** The wiki has `topics/` (synthesis), `research/` (one question and its current answer) and `plans/` (the current status of a plan, with no history), each with a `_FORMAT.md`, and the single pages `direction.md` (the current direction and principles) and `roadmap.md` (what comes next; a date about the world may appear in it), which `SCHEMA.md` defines. Every kind has front matter with `kind` (the kind of its folder), `sources` and, for a topic, research page or plan, a `title` and a `status` (topic `draft` or `current`; research `open` or `concluded`; plan `proposed`, `active`, `paused`, `done` or `dropped`). The formats carry no history date and show the evidence labels. `prism wiki lint` validates the front matter of each kind (`missing-<kind>-kind`, `invalid-<kind>-kind`, `invalid-<kind>-title`, `missing-<kind>-status`, `invalid-<kind>-status`, `missing-<kind>-frontmatter` and `invalid-<kind>-sources`, with `<kind>` one of `topic`, `research`, `plan`, `direction` and `roadmap`), applies the history-date, evidence-label, superseded-decision and relative-link checks to them, and the graph no longer reports a link to one of these pages as dangling.
- **`ingest`, a generic intake skill for any role and any page kind.** It processes one pending folder into a topic, research page, plan, direction, roadmap, persona, business rule, decision (ADR) or new feature, with the evidence labels, the date-slug processed source, the conflict quarantine and the current-state replacement rules. `po-intake` and `design-intake` remain the role-specific entry points. The connected board accepts `ingest` as a write skill (25 canonical skills) with a validator built on the intake validators: a new feature meets every `po-intake` rule; a topic, research page, plan, direction or roadmap page is created or replaced in place; a persona, business rule or decision is created and never rewritten, except that a new decision with `supersedes: ADR-NNN` comes with the old ADR changed in its status fields only (`record_immutable` and `supersession_incomplete` otherwise); the manifest lists every written page by path and canonical ID. New rejection codes are `invalid_topic`, `invalid_research`, `invalid_plan`, `invalid_direction`, `invalid_roadmap`, `wiki_path_invalid`, `invalid_decision` and `decision_path_mismatch`. The board's pending-intake panel offers `ingest` next to `po-intake`, and its card reads "awaiting intake".
- **The general index lists every wiki page.** `index.md` has one line per page, in the present tense, grouped by kind (`- [F-001 User login](features/F-001-login.md): Users sign in with an email address.`), with no dates and no narrative; a changed page's line is replaced in place. The connected board adds or replaces the line of each page it writes, derived from the page's title and the first sentence of its summary, and merges it by page with the same conflict, idempotence and recovery guarantees as the status rows (`stale_index_entry`, `duplicate_index_entry`). `prism wiki lint` reports `missing-index-entry`, `orphan-index-entry` and `duplicate-index-entry` as warnings on `index.md`; they never block a lifecycle action.
- **A "Project docs" group in the general index.** A generated workspace's `knowledge/wiki/index.md` lists each template-owned `docs/` page once, as `- [Architecture](../../docs/architecture.md): System design, platform map, tech decisions and the auth flow.`, so an agent finds the human docs from the wiki. `prism wiki lint` holds these lines to the rules of the other index lines: `orphan-index-entry` for a line whose doc does not exist and `duplicate-index-entry` for a doc listed twice. A doc without a line is not a finding, and `wiki search` does not return docs. A workflow-only workspace has no such group.
- **`prism workflow install` adds the index lines of the pages it installs.** When it keeps your own `knowledge/wiki/index.md`, it appends a line for each page it creates (`CONNECTED.md`, `status-board.md`, `direction.md`, `roadmap.md` and similar), in that page's group, and changes no line you wrote, so adoption no longer leaves `missing-index-entry` warnings for those pages.
- **`prism wiki search` and `wiki-query` read the index first.** The index lines that contain the query name their pages, which come first in `facts.results` with their `index_line` and `index` among the `matched_fields`; `facts.index_match_count` counts them, and the index is listed first under `sources`. Every page folder, including the new kinds, is still searched by its own fields. The `wiki-query` skills say so in both layers.
- **Evidence labels on current-state pages.** `SCHEMA.md` defines five labels, written as a bold run-in label at the start of a list item or paragraph: `**Decided:**`, `**Observed:**`, `**Proposed:**`, `**Assumed:**` and `**Unknown:**`. A Decided or Observed claim links its evidence: a processed intake item, a record or a URL. A feature's `## Open questions` table is its Unknown form. Each page format's example shows the labels, and operational rules 12 to 15 state the current-state rule (replace superseded content in place, rationale as a current fact, history in `log.md` and the records), the labeling rule, the rule that records and raw sources are never rewritten, and the quarantine rule. `prism wiki lint` reports a Decided or Observed item without a link as the warning `unlinked-claim`, and a bold run-in label that is none of the five as the warning `unknown-evidence-label`. Lint checks the form only and never whether the evidence supports the claim.
- **Decision supersession.** An ADR can carry `supersedes: ADR-NNN`, and a superseded ADR carries `status: superseded` and `superseded-by: ADR-MMM` with its body unchanged. `SCHEMA.md` defines the decision-supersession workflow as one operation that also updates the current-state pages that relied on the old decision. `prism wiki lint` reports links that disagree or are missing as the error `supersession-mismatch`, and a current-state page that links a superseded ADR as the warning `superseded-decision-cited`.
- **Dated, immutable raw sources.** Intake folders are named `YYYY-MM-DD-slug/` under `pending`, `processed` and `quarantined`, and a processed item keeps a `MANIFEST.md`. The connected board rejects a move whose folder has another name with `intake_name_invalid`, and a write into an existing processed item, or a move onto one, with `processed_source_immutable`. `prism wiki lint` warns with `processed-source-without-manifest` when a processed item has no manifest. `intake/README.md` says how to archive an agent review packet or an agent output as a source, and the intake templates carry a `Captured:` line that matches the folder's date. `design-intake` writes a `MANIFEST.md` in the processed folder it creates, listing the design page and the feature by path; a proposal without it is rejected with `intake_manifest_scope` or `intake_manifest_incomplete`, because every processed item has a manifest.
- **Conflict quarantine records.** A source that contradicts an existing page moves to `intake/quarantined/YYYY-MM-DD-slug/` with a `CONFLICT.md`: front matter `status: open | resolved`, and an `## Existing claim` and an `## Incoming claim` section, each with `**Claim:**`, `**Scope:**` and a linked `**Evidence:**`. The existing page stays untouched until a human resolves the conflict. `prism wiki lint` reports each open conflict as the warning `unresolved-conflict` (a non-empty quarantine is not a gate) and a record that does not follow the format as the error `malformed-conflict`. The board accepts a quarantine only as a valid `CONFLICT.md` with `status: open` and no wiki change (`conflict_report_invalid`, `quarantine_write_scope`).
- **`history-date-on-page`, `malformed-log-entry` and `missing-schema-version` lint findings.** `prism wiki lint` reports a history-date field (`introduced`, `last-updated`, `created`, `updated`, `date-updated` and similar, in any spelling) in the front matter of a current-state page as the error `history-date-on-page`, with a message that points to `log.md`. An ADR keeps its `date` and an advisory review its `reviewed`, because a dated record's date is part of what it records. A `log.md` entry that is not in the log format is the warning `malformed-log-entry`: lint reports it and never rewrites the log. `SCHEMA.md` and `LIFECYCLE.md` start with the front matter `schema-version: 1`, and one without it is the error `missing-schema-version`.
- **Link and source checks.** Every relative Markdown link and every `sources` entry of a wiki page must resolve to an existing file or folder. `prism wiki lint` reports one that does not, or that leaves the workspace, as `broken-link` (the former `broken-wiki-link`, which covered only links to wiki pages) (error, naming the page, the link and the line), and an anchor that no heading of its target gives as `broken-anchor` (warning). Links in code, URLs, images and absolute paths are not checked, and no URL is fetched. A feature's `sources` entries are paths; a persona, business rule, topic, research page, plan, `direction.md` or `roadmap.md` may hold URLs or free text, so only an entry that is a `knowledge/` path is checked, and a pending intake path names the processed path to list. Only a broken link to a page of the wiki gates a lifecycle action, as before; the other link findings never block.
- **`repo:<repository-id>/<path>` links into an external repository.** In a body link or a `sources` entry, `repo:mobile-apps/apps/partner/Login.kt` names a file or folder of a repository of `prism.workspace.yml` (`workspace` is this repository). Lint resolves it through the untracked `prism.local.yml` and only checks that the path exists: it never reads a file in a checkout, never follows a symlink inside one and never writes there. A repository with no checkout gives one `external-repository-unresolved` warning for that repository, however many links point into it, and its links are skipped. A path missing from a resolved checkout, an undeclared repository id and a malformed link are `broken-link`. `SCHEMA.md`, `docs/workspace-model.md` and `docs/wiki-workflow.md` define the form.
- **Freshness from the log.** A verification is a `log.md` entry whose operation is `verify`; the pages on its `paths` line were checked against their sources that day. For each current-state page, lint takes the latest `verify` entry that lists it and reports `stale-page` (warning) when it is older than `wiki-stale-after-days` (14 when `SETTINGS.md` is absent or invalid) and `never-verified` (information) when there is none, so an overdue page is not confused with one that nobody has checked. Records, the log, the index, the status board, the schema files and generated files are exempt. Freshness never changes a status and never blocks a lifecycle action or a board write. `never-verified` appears in `prism wiki lint` and its JSON only; `stale-page` appears wherever diagnostics do, and it keeps a graph node healthy. This replaces the date-based `stale-page` warning, because pages carry no date. The `wiki-owner`, `lint-wiki` and `wiki-blockers` skills, `docs/generated-projects.md` and the generated `AGENTS.md` describe staleness as the log-derived `stale-page`, and the direct-read fallback of `wiki-owner` computes it from the `verify` entries of `log.md`.
- **`prism wiki verify <page>... [--evidence <link>] [--by <name>]`.** It appends one `verify` entry to `knowledge/wiki/log.md` and changes nothing else. A page is named from the workspace root or from the wiki. The command refuses a path outside the wiki, a page that does not exist and a page that is not a current-state page, and writes nothing when it refuses any page. It appends the way the board does: it rejects a symlink or reparse point on the path, swaps the log in atomically only while it is unchanged and reads it again when another writer got in between.
- **`verify-pages`, a canonical skill that records a verification through the board.** `preview_skill` with an empty `changes` list and the verified pages in `read_revisions`, each with the digest `read_workspace` returned, previews one `verify` entry in `log.md`; `apply` is refused as stale when a verified page changed after the preview. Like every skill write it is for agents, and the entry's `by` names the agent. `verify-pages` is the 26th canonical skill; the packaged workflow asset and its digest change, so existing grants need `prism workflow upgrade`.

### Changed

- **The packaged skills require `prism-kit>=0.5.0`.** The skills and the generated `AGENTS.md` use commands and formats that 0.5.0 introduced (`ingest`, `prism wiki verify`, the status board and the log format), so their CLI probe accepts `prism 0.5.0` or newer.
- **`prism wiki lint` lists the warnings and information of a wiki without errors.** After `Wiki contract checks passed.` it prints a Findings section; before, only the counts showed.
- **An ADR's status is `superseded` with a `superseded-by` field.** The earlier `status: superseded-by ADR-XXX` form is an `invalid-decision-status` error.
- **The intake skills, writing skills and guidance follow the new rules.** `po-intake` and `design-intake` take a `YYYY-MM-DD-slug` folder, label and link every claim, update a changed fact in place, and quarantine a contradiction with a `CONFLICT.md`; `po-specify`, the clarify skills, `design-handoff`, `dev-done`, `board-review` and `setup-project` name the labeling and current-state rule; `lint-wiki` lists the new findings; the root guidance and the Cursor wiki rule state the rules. The `feature new` generator creates a dated intake folder.
- **`log.md` is the only home for history, and every entry has one structured shape.** An entry is `## YYYY-MM-DD <operation> | <subject>` followed by `- paths:` (the changed paths), `- evidence:` (links to evidence, never copied evidence) and `- by:` (the actor), and at most one optional line of plain text. `SCHEMA.md` defines the format, states that the log is append-only, and states the rule for pages: a current-state page carries no date about itself, a date about the world stays in the page, and an ADR, an advisory review and each `## Reopen history` entry keep their own date as dated records. The board's entries use the format with `evidence: board preview <id>` and `by: <name> (<kind>)`, and keep the preview marker and the actor as HTML comments; a move's processed intake folder is listed under `evidence`. The skills, commands and the Cursor advisory rule that append to the log name the format, and `setup-project` appends its entry in it. The template `log.md` starts with no entry.
- **The feature status board is its own file, `status-board.md`, and has no date column.** `index.md` is now the general index of every page. The board service manages `status-board.md` exactly as it managed the status rows (merge by feature, `stale_status_row` and `duplicate_status_row`, recovery), the write role is `status-board`, and a proposal that supplies `status-board.md` is rejected with `managed_file`. A workspace needs `status-board.md` besides `index.md`, `SCHEMA.md` and `LIFECYCLE.md`, or the board stays read-only and lint reports `missing-required-wiki-file`. The file lists `| ID | Feature | Status | Owner | Board Review |`; the board renders, merges and reads only that header, a table with an `Introduced` column is refused as `invalid_status_board`, and lint reports it as `malformed-status-board`. The lint codes of the status table are `malformed-status-board`, `feature-missing-from-status-board`, `status-board-missing-feature` and `status-board-frontmatter-drift`. The lifecycle skills, the guidance files and the Cursor rules read and update the status board row, and the packaged `wiki-*`, `feature-status` and `prep-sprint` skills read `status-board.md` for feature status.
- **A board transition writes no date.** `preview_transition` and `apply` change `status` and `owner` in the feature front matter and nothing else, and the lifecycle, clarify and design-intake checks no longer allow any date field. The packaged `po-specify`, `design-handoff` and `po-intake` guidance no longer asks for one.
- **The status board's "Recently updated wiki pages" report section is "Recently changed wiki pages"** and lists the paths of the newest `log.md` entries.
- **`AGENTS.md` is the single source of agent rules in a generated workspace, and `CLAUDE.md` imports it.** The root `CLAUDE.md` is the one line `@AGENTS.md`, and each platform folder (`backend/`, `web-user-app/`, `web-admin-portal/`, `mobile-android/`, `mobile-ios/`) repeats the pattern: its `AGENTS.md` holds the rules and its `CLAUDE.md` is `@AGENTS.md` plus the Claude Code skills and commands that no other tool shares. A platform `AGENTS.md` points at the root wiki workflow instead of restating it, and operations are named without a `/` or `$` prefix, with one section that gives the prefix of each tool. The platform `CLAUDE.md` skill lists name the skills as plain names: their `@.claude/skills/...` paths resolved relative to the platform folder and pointed at nothing. `.cursor/rules/project.mdc` is the one always-on rule and references `@AGENTS.md`; the CLI read-surface and fallback rules that only `wiki.mdc` carried are in `AGENTS.md`, and the scoped stack rules (`backend`, `web`, `mobile-android`, `mobile-ios`, `api-conventions`) and `advisory-review` stay. `prism workflow install` writes the same layout for a new workspace: `AGENTS.md` carries the connected-workflow section (with the knowledge-root paragraph for a knowledge root) and `CLAUDE.md` is `@AGENTS.md`; an existing `AGENTS.md` or `CLAUDE.md` is still preserved, and the plan offers to add the `CONNECTED.md` pointer to `AGENTS.md` and `@AGENTS.md` to `CLAUDE.md`. `prism validate` and workspace detection look for `AGENTS.md` where they looked for `CONTEXT.md`. `sync-ai-context` checks the single-source layout: the import layout of `AGENTS.md` and `CLAUDE.md`, the scoped Cursor rules, and the `.claude/` and `.agents/` skill packagings, which cannot import each other. The packaged workflow asset has a new digest, so existing board grants need to be issued again.

### Removed

The `invalid_last_updated` board error and the lint codes `invalid-feature-date`, `invalid-design-date`, `invalid-business-rule-introduced`, `invalid-persona-introduced` and `invalid-wiki-date` are gone with them.

## [0.4.0]

Release date: 2026-10-06

Prism 0.4.0 replaces the five fixed platforms with an application model that the workspace declares: `prism.workspace.yml` is `schema_version: 2` and lists repositories and apps, and features, lifecycle gates, status, the board and the graph read apps and their capabilities. The wiki schema is split into `SCHEMA.md` and `LIFECYCLE.md`. A workflow-only workspace can be a knowledge root that holds the shared wiki for apps in other repositories. Prism has no users of earlier versions, so workspaces created with 0.3.0 or earlier must be recreated; there is no upgrade path.

### Added

- **Knowledge-root workspaces.** `prism workflow install PATH --name NAME --knowledge-root` starts a workflow-only workspace with no apps that holds the shared wiki for apps living in other repositories, and records `workflow.purpose: knowledge-root` beside `workflow.mode: workflow`. The option belongs to `install`, starts a new workspace and cannot be combined with `--app`; register the external apps with `prism app add --repository … --remote …` and map their checkouts in `prism.local.yml`. The purpose is optional and has one valid value, and any other value (or a purpose on a generated workspace) is the error `invalid-workflow-purpose`. No gate reads it. `prism status` shows `Purpose: knowledge root` and says there are no features yet, `workspace.purpose` appears in `prism status --json`, `prism wiki lint --json`, the wiki queries and the graph (and `board.purpose` in the board's `discover`) for a knowledge root only, the board page shows a "no features yet" guide, and the installed `AGENTS.md` and `CLAUDE.md` describe the workspace as a knowledge root with the coordination contract for external repositories. The guidance comes from the "Connected board workflow" section of the root guidance templates through a `knowledge_root` condition (`knowledge_root_pointers` is new in the packaged workflow asset). With no features, with or without external apps, `prism wiki lint`, `prism validate`, `prism status`, `prism doctor --workspace` and the board pass; an external repository without a checkout is one warning. `docs/workspace-model.md` has the worked example and the README quickstart one line about it.
- **`prism presets` lists workflow presets.** The knowledge root is listed with its command under "Workflow presets", apart from the generation presets, and `prism presets --json` (new) returns `generation_presets` and `workflow_presets`.
- **`prism app list` and `prism app add`.** `prism app list [PATH] [--json]` shows the workspace's apps and repositories. `prism app add ID --stack STACK` previews, and with `--apply` (and `--yes` for automation) writes, one app in `prism.workspace.yml`, with `--name`, `--repository`, `--remote`, `--path`, `--audience`, `--has-ui` and `--serves-api`. It never generates code. `--remote` declares a new external repository together with its first app, an `other` app must declare both capabilities, and a path in this repository that does not exist yet is a warning. The manifest is validated before anything is written; any error writes nothing. The command says that the board identity changed, so a running board must be restarted and grants reissued.
- **The workspace model guide.** `docs/workspace-model.md` describes stacks and capabilities, repositories and `prism.local.yml`, apps and their fields, the `prism app` commands, workspaces with no apps and an example with one external repository.
- **`prism app retire`.** `prism app retire ID [--apply] [--yes] [--json] [PATH]` previews, and with `--apply` writes, `status: retired` on one app in `prism.workspace.yml`, with the same plan, confirmation and write checks as `prism app add`. It deletes no code, wiki page, requirement page or evidence, lists the features before `done` that still name the app, and says that the board identity changed (restart the board and reissue grants). An unknown or already retired app is an error that writes nothing. A retired app stays in `prism app list`, status, the board's apps and the graph, marked `retired`.
- **Retired apps in feature scope.** A retired app stays valid in the `apps` of a feature that is `done`. A feature before `done` that still names it is flagged `app-retired-in-scope`: lint reports an error and every lifecycle action on that feature is blocked with that code until its `apps` is edited explicitly (retirement never changes scope by itself). A new feature, or an edit that adds a retired app to a scope, is rejected with `app-retired` (`app_retired` on the board; `app_retired_in_scope` for a lifecycle proposal on a flagged feature). Adding an app never changes an existing feature's `apps`.
- **API work needs an app that serves an API.** When a feature's `## API surface` declares API work, at least one active app in its `apps` must have `serves-api` (`unknown` counts as true). Lint reports `api-surface-without-api-app` for features before `done`, the `design-handoff`, `dev-start` and `dev-done` transition checks block with that code, and the board rejects a `design-handoff` proposal with `api_surface_without_api_app`.

A Copier run without the CLI names no minimum (`0.0.0`). During `prism update` the saved template renders with the version recorded in the manifest's `generated_by`, so an unedited minimum advances with the template and an edited one is reported as a competing edit.

The packaged JSON schemas describe the new shape. `prism status` and `prism doctor --workspace` show an apps table (ID, name, stack, repository, path, status, maturity) and one line per external repository, and the board page's workspace summary and generated prompts say "apps" and list their IDs.

The plan and receipt list `apps` instead of `platforms`. A new workspace installed without `--app` has no apps instead of failing. The questionnaire, presets and `prism new` keep their `platforms` answer.

The checks that run for the five generated apps and a preset are the same as before.

- An API surface of `None.` or `No API changes identified.` no longer counts as declared API work. It blocked `dev-start` and `dev-done` with "A substantive API surface requires a matching API contract page" and made lint fail a done feature; lint and the transition preflight now share one rule (empty, or a plain statement that there is none, with or without a closing period).
- A rejection for changing a section outside an action's scope (`lifecycle_body_scope`, `clarify_scope_exceeded` and the design and requirement variants) names the sections to restore in the message and in `details.sections`. `linked_page_scope` names the linked page in the message and in `details.path`.
- A platform requirement that links its own feature page in `## Dependencies` is no longer reported as depending on an unfinished feature, which blocked `dev-start`. A link to another unfinished feature still is.
- `prism doctor` reports `No active grants (N revoked).` when grants exist and all are revoked, instead of `No grants yet.`
- `prism board serve` reports a client's reset connection (`ConnectionResetError`) with one quiet line instead of a traceback each time.
- `prism new` without `--template` ends with one message and exit code 3, instead of a Copier traceback and exit code 5, when the template release tag that matches the installed version is not published. The message points to `--template <path or URL>` or a released version.
- `prism doctor --workspace .` in a generated project suggests `prism workflow upgrade` for a missing workflow pin, because `prism workflow install` refuses generated workspaces.
- `prism doctor`, run without a target inside a workflow or generated workspace folder, points to `prism doctor --workspace .` instead of saying that you can generate a project.
- `prism board serve` flushes its banner lines, so a pipe or a log file shows the board URL while the service runs instead of only at exit.
- The board shows the new stage right after an apply or a recovery, because the board snapshot is refreshed before the operation answers.
- A live update that arrives before the apply response no longer replaces "Operation applied" with a stale-preview warning.
- An apply rejected because its sources changed shows the service's reason and a **Preview again** action, instead of an "outcome unknown" operation that was never created. An apply after the session expired shows the expiry message and **Reconnect**.
- After the board service restarts, the page shows "Board session expired · Reconnect" instead of staying STALE.
- `prism board serve` stops promptly on Ctrl+C while a browser is connected.
- Dropping a card on a column that does not accept it explains why, also to screen readers.
- Every board dialog keeps keyboard focus inside it, including Shift+Tab from the heading, and the header no longer scrolls sideways at tablet width.
- Generated web apps no longer describe themselves as based on another application.
- Generated Android app: a first-launch crash from the welcome-slide drawables, a nonexistent instrumentation runner and instrumentation test names that failed dexing.
- Generated web apps: the Microsoft provider ID is `microsoft-entra-id`, and a rejected backend refresh ends the web session.
- `docs/cli-release.md` points to the current acceptance record.
- **A write path Windows cannot hold is rejected at preview.** A path segment that contains `:` `<` `>` `"` `|` `?` `*` or a control character, ends in a dot or a space, or is a reserved device name (`CON`, `NUL`, `COM1` and the others, with or without an extension) is rejected with `invalid_path` on every operating system. Before, a path such as `F-001-document-review.md:stream.md` passed preview, and apply failed partway through, left the workspace half written and kept the operation unresolved.
- **`feature-reopen` archives every delivery-evidence table that `dev-done` accepts.** Both now read the table with one parser, so column order, header case, emphasis in the header and the case of the platform ID no longer decide. Before, a feature completed with a reordered table or a capitalised platform could never be reopened through the board. The reopen record still has to repeat each prior row verbatim, in the table's own column order.
- **A resolved answer is matched as whole words in the clarify skills.** The traceability check no longer accepts `no` inside `not`, `know` or `notice`; case and whitespace are still ignored.
- **`changes` and `query` no longer drop an item larger than one result.** An oversize event is returned in chunks (`event_chunk`, continued with the cursor `N~K`), and an oversize `query` item is replaced by an entry that names it and says to read its path with `read_workspace`. Before, the cursor moved past it and a client never saw it.
- **HTTP Bearer clients can page.** `POST /api/board/v1/workspace/read` and `POST /api/board/v1/query` accept an optional string `cursor` and return `next_cursor`, as the MCP tools do.
- **An intake proposal can no longer link the pending folder it moves.** `po-intake` wrote `sources: [knowledge/intake/pending/<folder>]` on a new feature page while the same proposal moved that folder to `knowledge/intake/processed/<folder>`, so the page linked a folder that no longer existed and the next agent stopped because it could not read its source. A new `sources` entry (a feature's `sources`, a persona's `sources` or a business rule's `source`) that lies under `knowledge/intake/pending/` is now rejected with `intake_source_not_processed`, and one that will not exist once the proposal applies with `source_link_missing`; both carry `details` and the first names the processed path to list. A path counts as existing when it is on disk, is written by the proposal or is inside the processed folder the proposal's own move creates. An entry that is already on the page, a URL and a persona or business-rule entry that is not a `knowledge/` path are not checked, so an older stale link does not block an edit.
