# Workspace model

A Prism workspace declares what it contains in `prism.workspace.yml`: the repositories its code lives in and the apps in them. Every command that reads the manifest (`prism status`, `prism wiki lint`, the board and its MCP tools, `prism doctor --workspace`, `prism workflow install`, `prism update`) reads it through one normalizer, so they all report the same apps. This page describes the model and the `prism app` commands. [shared-board.md](shared-board.md) covers adopting the workflow, and [getting-started.md](getting-started.md) covers generating a project.

## Stacks and capabilities

Every app has a **stack** from a registry that ships with the CLI. A stack says what kind of application it is and what it can do.

| Stack | Generated by `prism new` | `has-ui` | `serves-api` | Default path |
| --- | --- | --- | --- | --- |
| `spring-backend` | yes | false | true | `backend` |
| `nextjs-web` | yes | true | false | none (the app ID) |
| `android-compose` | yes | true | false | `mobile-android` |
| `ios-swiftui` | yes | true | false | `mobile-ios` |
| `other` | no | must be declared | must be declared | none (the app ID) |

The two **capabilities** are `has-ui` (the app has screens that need design) and `serves-api` (the app provides an API). Each is `true`, `false` or `"unknown"`. A stack supplies defaults, and an app may override them with a `capabilities` mapping. An `other` app has no defaults, so it must declare both. Status, the board and `prism app list` report the resolved values.

## Repositories and `prism.local.yml`

An app lives in a repository. `workspace` is the repository that holds `prism.workspace.yml`; it needs no entry and is the default. Any other repository is declared in `repositories` with an `id` (a lowercase slug) and a `remote`, its canonical URL (`https://`, `ssh://` or `git@host:path`). A remote is never a local path or a `file:` URL, and it never carries credentials.

Each machine says where it keeps a checkout of an external repository in `prism.local.yml`, next to the manifest:

```yaml
repositories:
  mobile-apps: /home/me/src/mobile-apps    # an absolute path
```

`prism.local.yml` is per machine and is not committed: a generated project's `.gitignore` lists it, and `prism workflow install` adds the rule to an existing `.gitignore`. Without a usable entry for an external repository, the workspace still loads. Status shows one `external-repository-unresolved` warning for that repository and reports its `checkout` as `unresolved`; with a checkout that exists, the warning goes and `checkout` is `resolved`. Status never prints the local path. Prism only checks that the checkout exists. It does not read from it or write to it, and it ignores a `prism.local.yml` or a checkout that is a symlink or reparse point.

## Apps

An entry in `apps` has these fields.

| Field | Meaning |
| --- | --- |
| `id` | A stable lowercase slug, unique in the workspace. It is never reused. |
| `name` | A display name. It defaults to the ID, and renaming changes only this field. |
| `stack` | A stack from the registry. |
| `repository` | A repository ID. It defaults to `workspace`. |
| `path` | The app's directory, relative to its repository root with forward slashes. It defaults to the stack's default path. It is unique per repository, apps in one repository must not overlap, and it cannot be `.` in the workspace repository. |
| `audience` | Optional free text, for example `B2C`. |
| `status` | `active` (the default) or `retired`. |
| `capabilities` | Optional overrides of the stack's capabilities. |

`app_maturity` maps an app ID to `level` and `caveat`. Status shows each app's entry as `maturity`, and prints the caveats.

`prism new` registers the platforms you pick as apps with the IDs `backend`, `web-user-app`, `web-admin-portal`, `mobile-android` and `mobile-ios`, each in the `workspace` repository.

### Example: one external repository

```yaml
schema_version: 2
project:
  name: Acme
repositories:
  - id: mobile-apps
    remote: https://example.com/acme/mobile-apps.git
apps:
  - id: backend
    name: Spring Boot Backend
    stack: spring-backend
    repository: workspace
    path: backend
  - id: customer-android
    name: Customer app
    stack: android-compose
    repository: workspace
    path: apps/customer
    audience: B2C
  - id: partner-android
    name: Partner app
    stack: android-compose
    repository: mobile-apps
    path: apps/partner
    audience: B2B
```

Two apps share a stack, live in different repositories and appear separately in status and on the board, each with its own maturity.

## `prism app list`

```text
prism app list [PATH] [--json]
```

Shows the apps and repositories in the same table as `prism status`: ID, name, stack, repository, path, status and maturity, then one line per external repository saying whether its checkout is resolved, then any manifest findings. `--json` returns `apps` and `repositories` in the shapes below, plus the manifest `diagnostics`. The command exits with 3 when the workspace has no usable manifest.

## `prism app add`

```text
prism app add ID --stack STACK [--name NAME] [--repository REPO [--remote URL]] [--path PATH]
              [--audience TEXT] [--has-ui true|false|unknown] [--serves-api true|false|unknown]
              [--apply [--yes]] [--json] [PATH]
```

Registers an app in `prism.workspace.yml`. It edits the manifest only and never generates code.

- Without `--apply` it shows the exact manifest change and exits with 0, like the preview of `prism workflow install`. `--apply` writes it after you confirm, and `--apply --yes` skips the question for automation.
- `--path` defaults to the stack's default path, or to the app ID when the stack has none. The path of an app in this repository that does not exist yet is a warning, not an error.
- `--remote` is allowed only together with `--repository` naming a repository the manifest does not declare yet. The repository is then added with that remote. A later app in the same repository needs only `--repository`.
- An `other` app needs both `--has-ui` and `--serves-api`. For the other stacks the two flags override the stack's defaults.
- The new manifest is validated before anything is written. Any error stops the command with exit code 3 and writes nothing: a duplicate or invalid ID, an unknown repository, a path that is absolute, contains `..` or overlaps another app in the same repository, a remote that is a local path, or a missing capability. The write refuses a manifest that is a symlink or reparse point, and it replaces the file atomically and only if it did not change after the preview. Fields it does not touch keep their values.
- The app scope is part of the board identity. After the command, stop a running board and start it again with `prism board serve`, and reissue grants with `prism board grant` for any participant the board rejects. A running board disables writes with `workspace_identity_changed` until it is restarted.

There is no command to remove or retire an app. To retire one, set its `status` to `retired` in the manifest by hand.

Example, run in an empty workspace with `backend` registered:

```text
prism app add customer-android --stack android-compose --name "Customer app" --audience B2C --path apps/customer --apply --yes
prism app add partner-android --stack android-compose --name "Partner app" --audience B2B --repository mobile-apps --remote https://example.com/acme/mobile-apps.git --path apps/partner --apply --yes
prism status
```

## Workspaces with no apps

A workspace created by `prism workflow install` without `--app` has `apps: []`. It loads, lints, reports status (`Apps: none declared`) and is served by the board with writes enabled; `discover` lists no apps. Register apps later with `prism app add`.

An operation that needs an app scope still stops at its own check. A feature that names `backend` in a workspace with no apps is blocked at the `platform-scope` check of `po-handoff` and its preview, and a write that scopes a feature is rejected with `invalid_feature_output`. Both messages say that the workspace declares no apps and point to `prism app add`.

## What the output looks like

`prism status --json` reports `workspace.apps` and `workspace.repositories`. `prism wiki lint --json`, the wiki query commands and the graph report `workspace.apps`, and the board's `discover` reports `board.apps`.

```json
{
  "apps": [
    {
      "id": "partner-android",
      "name": "Partner app",
      "stack": "android-compose",
      "repository": "mobile-apps",
      "path": "apps/partner",
      "audience": "B2B",
      "status": "active",
      "capabilities": { "has-ui": true, "serves-api": false },
      "maturity": null
    }
  ],
  "repositories": [
    { "id": "workspace", "remote": null },
    { "id": "mobile-apps", "remote": "https://example.com/acme/mobile-apps.git", "checkout": "unresolved" }
  ]
}
```

`audience` and `maturity` are `null` when the manifest records none. `checkout` appears only for external repositories. The packaged schemas under `prism_cli/schemas/` describe the shapes.

## Feature scope

Feature pages still declare their scope in the `platforms:` front matter with the five generated app IDs, requirement files are named `F-XXX-<id>.md` with the same IDs, and `prism wiki platform` takes one of them. An app with another ID is registered, reported and bound into the board identity, but a feature cannot name it in its scope yet.
