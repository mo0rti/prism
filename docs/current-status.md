# Current Status

Prism's core is the workflow and the shared board that humans and agents use together. It runs on one computer: `prism board serve` starts one local service per workspace that serves the browser board and a standard MCP endpoint. Application generation is an optional way to start a workspace. The [core plan](prism-core-workflow-plan.md) states the scope and contracts. [Shared board](shared-board.md) is the usage guide, [troubleshooting](troubleshooting.md) covers failures, and [SECURITY.md](../SECURITY.md) is the threat model.

## Core

| Area | Current state |
| --- | --- |
| Wiki, queries, lint and lifecycle preflight | Implemented with regression tests. The nine lifecycle actions keep their exact source and owner pairs and their evidence rules. `prism wiki` commands, the `prism wiki graph` dashboard and static exports are read-only and copy-only. |
| Workflow adoption | `prism workflow install` and `prism workflow upgrade` preview every file, then apply on `--apply`. They work in empty workspaces, existing repositories and generated projects, and they do not generate application code. Cloud-synced folders such as OneDrive and Dropbox Files On-Demand are rejected. |
| Shared service | The local HTTP and MCP adapters share one service with revocable participant grants, exact previews, operation receipts and recoverable writes. A workspace opens read-only until its workflow pin matches this installation. |
| Apps and repositories | `prism.workspace.yml` declares repositories and apps; each app has a stack with `has-ui` and `serves-api` capabilities. Status, wiki lint and query output, and the board report `apps`, and status also reports `repositories`. `prism app list` and `prism app add` show and register apps without generating code, and a workspace may have no apps. [workspace-model.md](workspace-model.md) describes the model. A feature's `apps` names the apps the manifest declares, and the board's `feature-scope` skill edits it. |
| MCP tool contract 3 | Tool results are at most 48,000 characters. Long text and lists arrive in pages with opaque cursors and digests, `get_skill_reference` returns skill references, the server publishes orientation instructions, and `discover` lists the board's `apps`. A workspace pinned to an earlier workflow digest needs `prism workflow upgrade` and new grants, as [shared-board.md](shared-board.md#upgrading-a-pinned-workspace) describes. |
| Human board actions | The board performs `po-handoff`, `design-start` and `dev-start` directly. The other six actions stay with agent skills, which the board offers as a copyable MCP request. |
| Agent skills | 29 canonical skills are served through MCP. Connected writes are available for the skills that [shared-board.md](shared-board.md#work-together) lists. Custom skills keep the direct-file path. |
| `prism doctor --workspace` | A read-only "Shared board" section checks the cloud-sync location, the workflow pin, active grants, the default port and git ignore of `.prism/state`. Only `[fail]` lines change the exit code. |
| Smart template update | Needs a remote template source with a saved revision. A project generated from a local checkout records an unversioned snapshot that supplies no merge baseline, and `prism update --strategy recopy` is the explicit alternative. It updates the workspace layer and then each scaffolded app from its own answers file, on an update branch with one commit per layer, reports conflicts per layer and stops before merging when a layer conflicted. |
| Remote access | Not supported. The service listens on loopback only. |

## Validation

- `python -B scripts/run-tests.py` runs the Python regression suite across worker processes and prints one combined summary (`python -B -m unittest discover -s tests` runs the same tests in one process; [maintainer-workflow.md](maintainer-workflow.md#python-tests) describes the runner). The suite includes real MCP SDK transport tests, human and agent parity tests and the dashboard script harness. The POSIX terminal test is skipped on Windows, and the browser tests are skipped unless they are enabled.
- The browser suite in `tests/browser` drives the real board in Chromium through Playwright. Its scenarios cover pointer and keyboard apply, stale and lost-response handling, no-write paths, revocation and recovery, two viewers, event-stream reconnects and server restart, legacy and static copy-only views, `prism board serve` start and stop, and desktop, tablet and phone layouts with focus checks. Install the `e2e` extra (`pip install -e ".[e2e]"`), set `PRISM_BROWSER_E2E=1` and run `python -B -m unittest discover -s tests/browser -t .`. `PRISM_BROWSER_E2E_EXECUTABLE` selects an existing Chromium, and `PRISM_BROWSER_E2E_DIR` selects the folder for workspaces and screenshots. The `browser-e2e` job in `.github/workflows/cli-validation.yml` runs it and fails when every test is skipped. Visual sign-off on themes and viewports is an owner review, not an automated result.
- `scripts/check-installed-cli.py` exercises an installed CLI outside the source checkout, including generation and template updates. The `wheel` job in `cli-validation.yml` runs it.
- `./scripts/validate-template.ps1 -Mode contract` checks generated structure and workflows with actionlint, including a standalone selection of two web apps and workspaces with two Android apps and with two iOS apps. The default `full` mode also runs backend smoke checks. Both modes call the web helper with `-RunSmoke $false`.
- `.github/workflows/template-validation.yml` has separate `backend-smoke`, `web-smoke`, `android-build` and `ios-build` jobs; `web-smoke` generates a backend and two web apps through `prism new` and runs `npm ci`, lint, typecheck, the tests and the build in each web app, `android-build` generates a backend and two Android apps through `prism new` and runs `./gradlew assembleDebug testDebugUnitTest` in each, and `ios-build` generates a backend and two iOS apps and runs XcodeGen, a simulator build and the tests for each. The `golden-current` job checks that the committed `golden/` workspace (one app of each of the five stacks, generated from `scripts/golden-answers.yml`) equals a fresh generation, and each pack's job also runs the golden app's own generated workflow through `scripts/run-golden-workflow.py`, with the toolchain versions read from `packs/versions.yml` by `scripts/read-pins.py`. `web-smoke` and `agent-service` also audit the golden lockfiles (`scripts/audit-gate.py`): an advisory of high or critical severity fails the job unless it is listed below. A configured job is not evidence of a passing run.
- `tests/test_stack_skill_slice_paths.py` generates a workspace with all five stacks and fails when a stack skill cites a slice file that a generated app lacks.
- `scripts/measure-board-scale.py` measures a synthetic workspace at a chosen number of features (see below).

## Board performance

Board work grows about linearly with the number of features. On a synthetic workspace of 1,000 features, an idle change scan takes about 60 ms every 1.5 s, a preview about 1.1 s, an `apply` about 6.4 s, a blockers query about 1.9 s and a graph rebuild about 3 s. At 100 features, a preview takes about 0.3 s and an `apply` about 1.3 s. The change poller reuses file hashes for unchanged files and rehashes everything at least every 60 seconds. An edit that keeps both a file's size and modification time can go unnoticed by the poller for up to 60 seconds, while previews and applies always re-read the files they depend on. The [changelog](../CHANGELOG.md) lists the speed-ups.

**Budgets.** The board is held to these 95th-percentile budgets per workspace size. A change that exceeds one is a regression to fix, not a figure to loosen.

| Metric (p95) | 100 features | 500 features | 1,000 features |
| --- | ---: | ---: | ---: |
| Idle change scan, workspace unchanged | 0.04 s | 0.10 s | 0.20 s |
| Graph rebuild after a change | 0.6 s | 3.0 s | 5.5 s |
| `preview_transition` | 0.7 s | 2.5 s | 5.0 s |
| `query` blockers | 0.7 s | 2.5 s | 5.0 s |
| `apply` (`po-handoff`) | 1.6 s | 5.5 s | 12 s |
| Cold start to the first `/data.json` | 2.5 s | 5.0 s | 8.0 s |
| `/data.json` request | 0.05 s | 0.10 s | 0.15 s |
| CPU of one core, no viewers | 3% | 8% | 12% |
| Peak memory (RSS) | 128 MiB | 192 MiB | 256 MiB |

**Reference machine.** Windows 11 with an Intel Core i9-14900KF (32 logical cores) and CPython 3.12.7, with the board service and the measuring client in one process. A slower machine scales every row by one factor; do not loosen single rows.

**How to measure.** Run `python scripts/measure-board-scale.py --out <dir> --sizes 100,500,1000` with the interpreter that has Prism's board dependencies installed. It builds a deterministic synthetic workspace per size in a temporary folder under `--out`, measures the real service, HTTP app and MCP tools on disposable copies, and writes `scale-results.json` and `scale-results.md`. The figures are timings, so they are compared by hand against the budgets and are not asserted in unit tests.

**Guard.** `tests/test_board_hot_path_counts.py` counts the repeated work of the same paths (page parses, file opens, workspace fingerprints, graph-input validations, lint runs and graph builds) on workspaces of 24 and 48 features. The counts are exact on every machine, so a regression fails as a counted extra read, never as a flaky timing.

## Stack packs

Each stack is a pack: one tested slice, not a finished product. A pack's maturity is the `level` that the manifest records for a scaffolded app (`prism status` and the board show it). Three kinds of evidence stand behind a level: the CI jobs of `template-validation.yml`, which run on every change to `packs/`, `template/`, `template-skills/`, `prism_cli/` or `golden/`; real runs that a maintainer did by hand with the services and tools running; and the acceptance case of the app model. A configured job is not evidence of a passing run, and a hand run is evidence of that run only.

| Pack | Maturity | CI job | Real runs |
| --- | --- | --- | --- |
| `spring-backend` | baseline | `backend-smoke` (generate through `prism new`, build, test, package the boot jar, build the Docker image) | Yes: sign-in and profile read on JDK 21 with Docker; two backends side by side |
| `nextjs-web` | provisional | `web-smoke` (`npm ci`, lint, typecheck, tests and build of two web apps) | Yes: dev server and sign-in against a running backend, including a web app against a second backend |
| `android-compose` | baseline | `android-build` (`./gradlew assembleDebug testDebugUnitTest` for two Android apps) | Yes: an API 35 emulator against a generated backend, checked by hand |
| `ios-swiftui` | experimental | `ios-build` (macOS: XcodeGen, simulator build and tests of two iOS apps) | None outside CI |
| `python-agent-service` | provisional | `agent-service` (`uv sync --locked`, ruff, mypy, tests, fake-provider evaluation) | Yes: the service against a running backend; the Claude adapter has never run against the live API |

Every pack's job also runs the golden app's own generated workflow (`scripts/run-golden-workflow.py`), `golden-current` checks that `golden/` equals a fresh generation, and `contract-validation` checks the generated structure. `web-smoke` and `agent-service` audit the golden lockfiles for security advisories.

- **Backend (`spring-backend`, baseline).** One tested slice: the `users` table and migration, a repository, a service and the controller of `GET /api/me`, the shared error model, an OAuth2 resource-server configuration that requires an audience whenever an issuer is configured, and a local development identity. Its 66 tests pass on JDK 21: unit tests, and integration tests that boot the default profile (the token and JWKS routes answer 404, every token is rejected without an identity provider) and the `local` profile (a dev token, then `GET /api/me`, and the public key set that verifies the token, with its loopback refusals) against a PostgreSQL started by Testcontainers, so they need Docker and no credentials. Real runs through `prism new` (evidence records `C5b`, `RL-S`, `RL-C`): the app started with the `local` profile, signed in and read the profile, answered 404 from the token route under the default profile and refused to start with `local` plus a configured issuer; two backends at different paths and ports ran side by side on one database, one schema each; a web app generated against the second backend (port 8081) signed in and showed that backend's user while nothing answered on 8080. The dev identity is local development sign-in, not authentication: the real identity provider, the authorization policy and the database design are yours (the generated `security-auth` skill covers the replacement). The backend has no Kotlin style linter; its `check` task runs Gradle's `check` without the tests. No live deployment has been verified.
- **Web (`nextjs-web`, provisional).** Any number of web apps, each with a "Local development sign-in" (the backend's dev identity, which is not complete authentication), one page that shows `GET /api/me` through a client generated from the shared OpenAPI contract, 26 Vitest and Testing Library tests and a committed `package-lock.json`. `npm ci`, lint, typecheck, the tests and the Next.js build pass locally for a generated web app and in `web-smoke` for two. A real run (evidence record `RL-S`) showed the dev server listening on `127.0.0.1` only, `POST /api/session` refusing a request without `Origin`, with a foreign `Origin` and from a non-loopback bind, a local sign-in that sets an httpOnly cookie, and the home page showing the profile from `GET /api/me`. A Next.js route cannot see the socket peer, so the local-only walls are the loopback bind, the `LOCAL_DEV_SIGNIN` flag and the refusal of a non-loopback bound address. The tests use a mocked backend; sign-in against a running backend is checked by hand. No hosting configuration is generated, which is why the level is provisional.
- **Android (`android-compose`, baseline).** Any number of Android apps, each with a "Local development sign-in" screen (the backend's dev identity, which is not complete authentication), a profile screen that shows `GET /api/me` through a hand-written Retrofit client that a unit test checks against the shared OpenAPI contract, an in-memory session and no example business features. Its 37 JVM tests pass: both state holders against a fake client, the client against a MockWebServer, the contract check and a Compose UI test of the sign-in label under Robolectric. `./gradlew assembleDebug testDebugUnitTest` passes locally on JDK 21 (evidence record `RL-C`), and `android-build` runs the same steps for two Android apps. A real run on an API 35 emulator against a generated backend under its `local` profile signed in through `adb reverse`, showed the profile and signed out, reported an unreachable backend without `adb reverse`, and left no token in logcat. That run is checked by hand: no instrumented or emulator test is part of the pack, and no signing or store release is generated.
- **iOS (`ios-swiftui`, experimental).** Any number of iOS apps, each with a "Local development sign-in" (the backend's dev identity, which is not complete authentication and works in the simulator only), one screen that shows `GET /api/me` through a hand-written client kept to the shared OpenAPI contract, XCTest unit tests of both view models and the client, one XCUITest of the sign-in screen and an XcodeGen `project.yml`. Locally on Windows or Linux the pack's structure, identifiers, YAML and the contract paths of the client are checked. Swift compilation and the tests are verified only by the macOS `ios-build` job (Xcode 26.6 on the pinned `macos-26` image, two iOS apps of one workspace) and by each app's own workflow. No local macOS build, simulator run against a backend or device run is part of the evidence, which is why the level is experimental.
- **Agent service (`python-agent-service`, provisional).** Any number of agent services, each a FastAPI app that assists and never advises: `GET /api/health`, `POST /api/assist` (one agent turn through a provider interface with one read-only tool that reads the backend's `GET /api/me` with the caller's own token), a deterministic fake provider and a Claude API adapter, bearer-token verification against the key the backend's dev identity publishes at `GET /api/dev-identity/jwks` (or a configured issuer and audience) with a fail-closed startup and no shared secret, and the safety rules (untrusted data, an audit log with user and request IDs that never holds a token or a tool error message, a per-user budget that reserves capacity before each model call, no cross-user data, a notice). Its 86 pytest tests, `ruff`, `mypy --strict` and the evaluation case (fake provider) pass locally on Python 3.12 with uv (evidence record `RL-C`). A real local run through `prism new` (evidence record `AGT`) started the backend under `local` and the service against its JWKS, answered `POST /api/assist` with the tool's `GET /api/me` result, returned 401 without a token, answered 503 while the key source was unavailable and refused to start with no identity configured. **The Claude adapter is tested against a stub only. No call to the live API has been made, so until someone runs `task <app-id>:eval-live` with a real `ANTHROPIC_API_KEY`, treat the adapter as unproven.** No hosting configuration is generated.

**Acceptance of the app model.** The acceptance case of the two-app model (two apps of one stack in two repositories, plus a backend; [workspace-model.md](workspace-model.md)) passes in all six parts, end to end through the CLI on generated packs, and the tests of `tests/test_apps_surfaces.py`, `tests/test_delivery_and_retirement.py` and `tests/test_feature_scope_apps.py` keep it passing. Identity: `customer-android` in the workspace and `partner-android` registered in an external repository with a `remote` appear separately in `prism status` and on the board, each with its own maturity. Requirements: a feature scoped to both needs both requirement pages and fires both design gates. Delivery: `dev-done` fails with release evidence for one app and passes with evidence for both (an external app's evidence is a URL, so no local checkout is needed). Retirement: retiring `partner-android` flags the feature in progress and changes only `prism.workspace.yml`. Default workspace: the `full` preset passes status, board and lint. Unresolved checkout: a workspace without a `prism.local.yml` entry for the external repository loads with exactly one warning. A second in-workspace Android app scaffolded with `prism app add --scaffold` and the first one each build with Gradle (`assembleDebug testDebugUnitTest`, no failures).

A generated pack build is not evidence that human and agent collaboration works; core acceptance uses disposable neutral workspaces. The questionnaire asks for the project identity and the app list only: there are no auth, database, deployment or supporting-service questions. A backend app always gets a PostgreSQL development database in Docker Compose, and Azure Container Apps and Cloudflare/OpenNext deployment are worked examples in the generated `deployment` skill. No live deployment has been verified.

## Known dependency advisories

`scripts/audit-gate.py` audits the golden web app's `package-lock.json` (`npm audit --audit-level=high`) and the golden agent service's `uv.lock` (`uv audit --locked`) in CI. A finding that has no fixed version is accepted only when `packs/audit-allowlist.yml` lists it with its advisory link and the reason; every such entry is recorded here. The agent service has no finding. The web app has one advisory, which `npm audit` reports on five packages of one chain:

| Advisory | Package | Severity | Where it comes from | Why it is accepted |
| --- | --- | --- | --- | --- |
| [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) (CVE-2026-93687) | `braces` (all versions up to 3.0.3, the latest release; no patched version) | high | `eslint-config-next` 16.4.0 (the latest) pins `@next/eslint-plugin-next`, which pins `fast-glob` 3.3.1, which uses `micromatch` and `braces`. `npm audit` lists the chain as `braces`, `micromatch`, `fast-glob`, `@next/eslint-plugin-next` and `eslint-config-next`. | A stack overflow through deeply nested brace patterns that an attacker supplies. The chain is a devDependency run by `npm run lint`: `npm audit --omit=dev` reports nothing, no code of the app loads it, and lint expands only the project's own glob patterns. No move of a pin in `packs/versions.yml` removes it, and the fix `npm audit fix --force` offers is a downgrade to `eslint-config-next` 14.2.35. |

The entry is removed when `braces` or the Next.js lint plugin ships a fix: the gate warns when an entry matches no finding, and a Renovate pull request for the `nextjs-web` pack then carries the new lockfile.

## Evaluating application generation

Choose a focused app list, inspect the generated files, and run each app's own build and runtime checks. The default app IDs (`backend`, `web`, `mobile-android`, `mobile-ios` and `agent-service`) are workflow scope labels, even in an adopted workspace that has no matching application directory.

Read [maintainer-workflow.md](maintainer-workflow.md) for the maintainer commands and [getting-started.md](getting-started.md) for the generation path.
